# Output with ALV (SAP List Viewer)

> ALV output: SALV (`cl_salv_table`) for read-only lists, `cl_gui_alv_grid` for interactive grids, the legacy FM-ALV — an obsolete pattern; classic `WRITE` lists — legacy only.
> Related: `dynpro.md` (screen, PBO/PAI, container), `classes.md` (event handlers, dependency injection), `style.md` ("Screens and events"), `errors.md` (the ALV exceptions).

- **[P2]** Classic lists in productive programs are obsolete — use ALV (SAP List Viewer) instead (ABAPDocu: "Classic lists should no longer be used in live application programs. Use SAP List Viewer (ALV) instead of classic lists.").
- **[P3]** If a classic list stays for legacy, avoid the obsolete constructs in it: obsolete formatting, obsolete calculations, obsolete list events and obsolete spooling (ABAPDocu: obsolete statements in list processing).
- **[info]** ALV stack: for read-only simple lists — the SALV model (`cl_salv_table` factory, no manual field catalog); for interactive/full-grid features — `cl_gui_alv_grid` in a container. Container choice: `cl_gui_custom_container` (dominant — a custom screen area), `cl_gui_docking_container` (docking panel, no custom screen), `cl_gui_splitter_container` (several ALVs side by side). SAP GUI technology, prepares a dynpro screen.
- **[P2]** Legacy FM-ALV — `REUSE_ALV_GRID_DISPLAY`/`REUSE_ALV_LIST_DISPLAY` + the `slis_*` stack (`slis_t_fieldcat_alv`, `slis_layout_alv`, `slis_selfield`, `slis_t_event`, `REUSE_ALV_FIELDCATALOG_MERGE`): still ALV, but an obsolete FM pattern. Do not create new FM-ALV — use SALV/grid; it is not the same as a classic `WRITE` list.
- **[P3]** SALV events — `get_event( )` → `cl_salv_events_table`, handlers `on_user_command`/`on_double_click`. Both SALV and grid register handlers the same way — `SET HANDLER` on the event source instance (see the grid rule below); the SALV difference is only that the handlers come from `cl_salv_events_table` instead of being declared for `cl_gui_alv_grid`.
- **[P1]** Editable grid: mark editable columns via `lvc_s_fcat-edit`, `register_edit_event( )`, then validate in `check_changed_data( )` — do not read the grid cells directly for validation. <!-- rule: alv-editable-grid-check -->
- **[P3]** Selection — grid `get_selected_rows( )`/`get_selections( )` + `set_selection_mode( )`; do not track the current row manually.
- **[info]** Grid GUI status/title — see `dynpro.md`; grid callbacks — the grid-events rule below.
- **[P3]** Derive the columns from the output structure (SALV columns / `lvc_s_fcat` from the DDIC type) instead of a hand-built field list — dictionary texts (data element labels) are the single source — the FM `LVC_FIELDCATALOG_MERGE` builds the catalog from a DDIC structure name instead of a hand-filled `lvc_s_fcat`; where a DDIC label does not fit, centralize the `coltext`/`scrtext_l/m/s`/`outputlen` overrides in one field-catalog builder, not scattered per screen; hotspot/clickable cells — SALV `set_cell_type( if_salv_c_cell_type=>hotspot )` / `lvc_s_fcat-hotspot`.
- **[P3]** Build the output data and the ALV control in a class method, not inline in the PBO module; ALV events (toolbar, double-click, buttons) — separate handler classes with injected dependencies (see `style.md`, "Screens and events"; `classes.md`).
- **[P2]** SALV errors/exceptions — class-based (`cx_salv_msg`/`cx_salv_error`); handle them, do not swallow (`errors.md`: an empty `CATCH` is forbidden).
- **[P2]** Layout variants: give the layout a key — SALV `get_layout( )->set_key( )` / grid via the `set_table_for_first_display` params `is_variant` (type `disvariant`, `report = sy-repid`) + `i_save` (e.g. `'A'`); **does not exist:** the `lvc_s_layo` field `vari`. Do not weaken `save_restriction` without the team's say: saved variants are the user's work, destroy them only deliberately.
- **[P3]** Sorting/totals — display-level: SALV `get_sorts( )->add_sort( )` / `get_aggregations( )->add_aggregation( columnname = ... )` (grid — sorting via `lvc_t_sort`; totals via field-catalog `do_sum` / sort `subtot`, the grid — **does not exist:** an aggregation-table *parameter* there, unlike SALV) instead of pre-sorting the internal table just for the ALV.
- **[P2]** Grid events (double-click, toolbar, F4, edit) — a wrongly registered handler never fires (the feature silently does nothing); input validation belongs in the handler, not in business methods.
- **[P2]** OO grid subscribes directly via `SET HANDLER handler->on_double_click FOR grid` (where `grid` is the grid instance) — `FOR EVENT` belongs to the **METHODS** declaration of the handler, not to the registration: `METHODS on_double_click FOR EVENT double_click OF cl_gui_alv_grid.` + `SET HANDLER handler->on_double_click FOR grid`; `set_registered_events` is only for `cl_gui_alv_tree`/`cl_gui_toolbar`.
- **[P2]** Legacy grid — callbacks `i_callback_user_command`/`i_callback_pf_status_set`. For editable cells the grid needs `set_ready_for_input( )` in PBO after `set_table_for_first_display( )`.
