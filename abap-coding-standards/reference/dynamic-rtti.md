# Dynamic programming and RTTI

- **[P2]** Dynamics — only when static is impossible (generic by type/structure/field). Static is preferable: the compiler does not catch dynamic errors.
- **[info]** RTTS (Runtime Type Services) — the umbrella for **RTTI** (introspection: `cl_abap_typedescr=>describe_by_data( )`/`describe_by_data_ref( )`/`describe_by_name( )`/`describe_by_object_ref( )` → `cl_abap_elemdescr`/`cl_abap_structdescr`/`cl_abap_tabledescr`/`cl_abap_refdescr`; per-type navigation: `get_components( )`, `get_table_line_type( )`, `get_component_type( )`) and **RTTC** (type **cre**ation: `cl_abap_structdescr=>create( )` / `cl_abap_tabledescr=>create( ... )` / `cl_abap_elemdescr=>get_*`), then `CREATE DATA ... TYPE HANDLE`.
- **[P1]** `ASSIGN COMPONENT comp OF STRUCTURE <fs> TO <f>` (or `(compname)`) — only after checking the component exists (`cl_abap_structdescr->get_components` / `line_exists`): a missing component sets **`sy-subrc = 4`** and the field-symbol stays bound/undefined — it does not raise `CX_SY_ASSIGN_OUT_OF_RANGE` (ABAPDocu "ASSIGN": that exception is caused by the `RANGE`/`INCREMENT` additions — the assigned data object is not contained in the range; runtime error `ASSIGN_FIELD_NOT_IN_RANGE`). A dynamic (`(compname)`) assignment can raise `CX_SY_ASSIGN_ILLEGAL_COMPONENT` and leave `sy-subrc` unchanged — check the component existence first. `ASSIGN (name)` without a whitelist — see `security.md`. <!-- rule: assign-component-check-exists -->
- **[P2]** Dynamic component/field names — the source is not external, validate it (see `security.md`: `CL_ABAP_DYN_PRG`).
- **[P3]** `DESCRIBE FIELD lv TYPE typ [LENGTH len] [DECIMALS dec]` / `DESCRIBE TABLE itab LINES lv_lines` — only when one attribute is needed (in Unicode, `LENGTH` must be requested with `IN BYTE MODE`/`IN CHARACTER MODE`); full description — via RTTI.
- **[info]** Downcast — `CAST cl_abap_structdescr( lo_descr )` (or `?=`): `CAST` is typed and fails fast.
- **[P2]** Copying: `dobj2 = dobj1` copies tables/structures entirely; references — `REF #`/`CREATE DATA ... LIKE`; do not confuse a data reference with a copy.
- **[P2]** Dynamic internal table from a DDIC structure/type by name — `cl_abap_tabledescr=>create( p_line_type = CAST cl_abap_datadescr( cl_abap_typedescr=>describe_by_name( 'tabname' ) ) )` then `CREATE DATA dref TYPE HANDLE lo_tabdescr` and `ASSIGN dref->*`; the table kind is set via `p_table_kind` (`tablekind_std`/`tablekind_sorted`/`tablekind_hashed`). The default key kind for a `STANDARD` table is `P_KEY_KIND = KEYDEFKIND_DEFAULT` ("Default key", an empty key) — **not** `KEYDEFKIND_STANDARD`; for `SORTED`/`HASHED` the default is the standard key over all components. Read the line type back with `get_table_line_type( )` and its components with `cl_abap_structdescr` `get_components( )`/`components`. For a `HASHED`/`SORTED` table the key semantics (uniqueness, key fields) are fixed at creation — verify `has_unique_key`/`get_keys( )` before relying on a `READ ... WITH TABLE KEY` to be unique.
- **[P2]** `cl_abap_tabledescr` attributes describe the key: `table_kind`, `key` (key fields), `get_keys( )` (unique/non-unique key kind per key), `has_unique_key`, `get_key_aliases( )`. Use them to decide a dynamic `READ ... WITH TABLE KEY` / uniqueness rather than assuming because of the kind alone.
- **[info]** `cl_abap_typedescr` common attributes/methods usable generically: `kind` (`kind_elem`/`kind_struct`/`kind_table`/`kind_ref`), `type_kind`, `relative_name`; a navigation without a `CAST` — `describe_by_data` returns the most specific descriptor, so branch on `kind` with `CASE` before downcasting (a wrong `CAST` raises `cx_sy_move_cast_error`).
- **[P3]** Dynamic access to a field-symbol's/object's type at runtime — `RTTS` is preferred over `DESCRIBE FIELD` for anything beyond one scalar attribute; `DESCRIBE FIELD` reports only the static (declared) type of a variable, so for a **generic** field-symbol (`TYPE ANY`/`data`) it cannot answer the actual runtime type of the data object it points to — use `cl_abap_typedescr=>describe_by_data( <fs> )` (or `describe_by_data_ref`) instead.
- **[P2]** A dynamic method/attribute access — `CALL METHOD oref->(mname)` / `oref->(attr)` (or `ASSIGN COMPONENT` on the structure): names not known at compile time are a code smell — prefer a statically known interface/type and a `CASE` over a small closed set; a dynamic call defeats the compiler and the static analyzers (`style.md`).
- **[P3]** `CREATE DATA dref TYPE (name)` (data), `CREATE OBJECT oref TYPE (name)` (object), `TYPE HANDLE` (type descriptor) — the `TYPE (...)` form takes a **name**, the `TYPE HANDLE` form a **descriptor**; do not mix them. A `CREATE OBJECT` by name needs the class in the class pool / `#EC` pragma when the name is a literal.
