# Screens (Dynpro)

> Classic Dynpro screens and their ABAP side. "No business logic in modules" and selection screens — `style.md` "Screens and events".

- **[P2]** No business logic in a dialog module (`PBO`/`PAI`) — see `style.md` "Screens and events". The division of roles: a `MODULE ... OUTPUT` sets the screen state; a `MODULE ... INPUT` reads the screen field / ok-code and calls the class method — neither computes or writes directly.
- **[P2]** Always allow the user to leave: the first `MODULE ... AT EXIT-COMMAND` handles the cancel/back function code, before the field checks. A module that raises `MESSAGE ... TYPE 'E'` outside `FIELD`/`CHAIN` leaves no input-ready field — without an `AT EXIT-COMMAND` path the user is stuck.
- **[info]** Single-field check — `FIELD f MODULE mod` (+ `ON REQUEST`: run only when the field was changed). On `E`/`W`, only that field becomes ready for input again, PAI resumes after the `FIELD` statement, earlier modules are not re-run.
- **[P2]** Related fields — check together in `CHAIN … ENDCHAIN`, not as separate `FIELD`s: `CHAIN. FIELD f1. FIELD f2. MODULE check. ENDCHAIN.` On an error, **all** chained fields stay ready for input (separate `FIELD`s gray out the rest after an error). Conditional run — `MODULE m ON CHAIN-INPUT` (any field of the chain has input) / `ON CHAIN-REQUEST` (any changed).
- **[info]** `CHAIN` is meaningful only in PAI (in PBO it has no effect); it cannot be nested.
- **[P2]** The user command — as the **first** PAI action save and clear it: `save_ok = ok_code. CLEAR ok_code.` then dispatch `CASE save_ok`. Clearing `ok_code` at the *end* of the module does not protect against a handler that runs `LEAVE SCREEN`/`SET SCREEN` or is interrupted by a message — the stale function code stays in the field and re-fires on the next Enter. Do not drive control flow from screen-field values that also carry data; function codes carry navigation, fields carry data.
- **[info]** Dynamic screen changes at PBO — `LOOP AT SCREEN` and set the `screen` attributes (`invisible`, `input`, `active`, `required`, `group1..group4`, `name`): `screen-input = 0` disables input, `screen-invisible = 1` suppresses the display (on an active input-capable field it may only mask the content, keeping the field in the dialog and input-capable) — for a fully hidden and non-processed field use `screen-active = 0` (see below); `MODIFY SCREEN` applies the change. Group fields by `group1..group4` in the Screen Painter to toggle them as one block.
- **[P2]** GUI status and title — `SET PF-STATUS` / `SET TITLEBAR` (in PBO), not hand-made menu/button code; function codes come from the status. Function-key texts and the status belong to the dynpro, not to ABAP literals.
- **[info]** Navigation — `LEAVE TO SCREEN n` (stay in the same screen sequence, PBO re-runs), `CALL SCREEN n` (a separate screen sequence, returns to the caller). `LEAVE SCREEN` — leave the current screen and continue on the **next screen**: the statically assigned next screen or the one set by `SET SCREEN` (if it points to the current screen again, the screen is entered again — not a return to the caller). A called sequence ends and returns to the caller **only when the next screen is 0** — the explicit `LEAVE TO SCREEN 0`; `SET SCREEN n` + `LEAVE SCREEN` — leave then call; `LEAVE PROGRAM` (end). `LEAVE TO LIST-PROCESSING` — switch to a classic list (see `alv.md` — prefer ALV over the list).
- **[P3]** Subscreen / tabstrip: `CALL SUBSCREEN` embeds another screen's PBO/PAI; a tabstrip switches subscreens — the embedded screen has its own flow logic. Do not fake tabs with `SET SCREEN` and duplicated fields.
- **[info]** `LOOP AT SCREEN` attributes: `screen-name` (dynpro field name), `screen-group1..group4` (attribute groups from the Screen Painter), `screen-input` (ready for input), `screen-required` (`1` = required (the automatic check runs on PAI); the special value `2` = **recommended field** — displayed as required but **no check is performed**; `0`/initial — normal), `screen-active` (`1` active/`0` hidden via the active flag — combined with `MODIFY SCREEN` this is the way to fully remove a field from the dialog; a field hidden with `screen-active = 0` is not processed on PAI), `screen-invisible` (display suppressed — alone it can mask the content of an active input field rather than remove it, and it does not stop PAI processing), `screen-output` (output-only), `screen-intensified` (highlight). Do not toggle visibility and then validate a field the user cannot see; hiding/deactivating a UI field is not a substitute for the business authorization/validation check behind it.
- **[P2]** Selecting screen fields to change — prefer `screen-name = 'FIELD'` for one field or `screen-group1 = 'GRP'` for a group; a plain substring match on `screen-name` (e.g. a range over a `MATNR`-like set) is fragile — set explicit groups in the Screen Painter for blocks you toggle together. Reversing a change on the next `LOOP AT SCREEN` without `MODIFY SCREEN` has no effect — each attribute change must be followed by `MODIFY SCREEN` to be applied.
- **[P3]** `screen-required = '2'` shows a field as required without checking it — for a *dynamic* (condition-dependent) requirement use `screen-required = 1` in PBO; there is **no** `REQUIRED` addition on `FIELD`/`CHAIN` in the flow logic (`FIELD` takes only `MODULE` and `WITH`) — a required-field check is a `MODULE` with `MESSAGE TYPE 'E'`, the visual hint is `screen-required`.
- **[info]** Input readiness on error: for `FIELD f MODULE m` — after an `E`/`W` message only field `f` returns to ready-for-input, so the user can correct just that field; for a `CHAIN`, all chained fields stay ready (see above). A module that sends `MESSAGE ... TYPE 'E'` **outside** a `FIELD`/`CHAIN` (i.e. a plain `MODULE` at PAI top) blanks the whole screen back to not-ready — combine with `AT EXIT-COMMAND` so the user is not locked in (already above).
- **[P2]** `ok_code`/user command: the function code from a pushed button / function key arrives in the global field **named on the dynpro** (the OK-code field, conventionally `ok_code`) — `SET PF-STATUS` does not set that field name, it belongs to the screen; check it with `CASE ok_code. WHEN 'BACK'. LEAVE TO SCREEN 0.` in the `AT EXIT-COMMAND` first module. Do not use free-text `FCODE` beyond the GUI status — see `style.md` "Screens and events" for separation of navigation (function codes) from data (fields).
- **[P3]** `SET CURSOR FIELD f` (place the cursor) / `SET CURSOR LINE n` — to direct focus (e.g. back to the offending field after a check); combine with `MESSAGE ... TYPE 'E'` so the message and the cursor point to the same field. Do not invent focus control values.
- **[P3]** Do not transport values from screen to program with implicit work areas — use the field with an explicit `TYPE` (see `data.md`, no `TABLES`); the dynpro field and the ABAP variable are the same name by convention, not by the work-area mechanism.

> Sources: SAP Help "Input Checks in Dialog Modules" (CHAIN/FIELD/MODULE, ON CHAIN-INPUT, message handling), ABAPDocu "Dynpro".
