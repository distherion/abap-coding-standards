# Screens (Dynpro)

> Classic Dynpro screens and their ABAP side. "No business logic in modules" and selection screens — `style.md` "Screens and events".

- **[P2]** Division of roles in the flow logic: a `MODULE ... OUTPUT` sets the screen state; a `MODULE ... INPUT` reads the screen field / ok-code and calls the class method (see `style.md`, "Screens and events").
- **[P2]** Always allow the user to leave: the first `MODULE ... AT EXIT-COMMAND` handles the cancel/back function code, before the field checks. A module that raises `MESSAGE ... TYPE 'E'` outside `FIELD`/`CHAIN` leaves no input-ready field — without an `AT EXIT-COMMAND` path the user is stuck.
- **[info]** Single-field check — `FIELD f MODULE mod` (+ `ON REQUEST`: run only when the field was changed). On `E`/`W`, only that field becomes ready for input again, PAI resumes after the `FIELD` statement, earlier modules are not re-run.
- **[P2]** Related fields — check together in `CHAIN … ENDCHAIN`, not as separate `FIELD`s: `CHAIN. FIELD f1. FIELD f2. MODULE check. ENDCHAIN.` On an error, **all** chained fields stay ready for input (separate `FIELD`s gray out the rest after an error). Conditional run — `MODULE m ON CHAIN-INPUT` (any field of the chain has input) / `ON CHAIN-REQUEST` (any changed).
- **[info]** `CHAIN` is meaningful only in PAI (in PBO it has no effect); it cannot be nested.
- **[P1]** The user command — as the **first** PAI action save and clear it: `save_ok = ok_code. CLEAR ok_code.` then dispatch `CASE save_ok`. Clearing `ok_code` at the *end* of the module does not protect against a handler that runs `LEAVE SCREEN`/`SET SCREEN` or is interrupted by a message — the stale function code stays in the field and re-fires on the next Enter. Do not drive control flow from screen-field values that also carry data; function codes carry navigation, fields carry data. A stale function code means the wrong action runs on the next Enter — a wrong write, not a cosmetic defect. <!-- rule: ok-code-save-clear -->
- **[info]** Dynamic screen changes at PBO — `LOOP AT SCREEN` and set the `screen` attributes: `screen-name` (dynpro field name), `screen-input` (`0` disables input), `screen-invisible` (`1` suppresses the display — on an active input-capable field it may only mask the content, keeping the field in the dialog and input-capable; it does not stop PAI processing), `screen-active` (`0` hides the field via the active flag — the way to fully remove it from the dialog; such a field is not processed on PAI), `screen-required` (`1` = required, the automatic check runs on PAI; the special value `2` = **recommended field** — displayed as required but **no check is performed**; `0`/initial — normal), `screen-group1..group4` (attribute groups from the Screen Painter), `screen-output` (output-only), `screen-intensified` (highlight).
- **[P2]** GUI status and title — `SET PF-STATUS` / `SET TITLEBAR` (in PBO), not hand-made menu/button code; function codes come from the status. Function-key texts and the status belong to the dynpro, not to ABAP literals.
- **[info]** Navigation — a called sequence (`CALL SCREEN n`) returns to the caller **only when the next screen is 0** (the explicit `LEAVE TO SCREEN 0`).
- **[P3]** Subscreen / tabstrip: `CALL SUBSCREEN` embeds another screen's PBO/PAI; a tabstrip switches subscreens — the embedded screen has its own flow logic. Do not fake tabs with `SET SCREEN` and duplicated fields.
- **[P1]** Hiding or deactivating a UI field is not a validation and not an authorization: a field the user cannot see must not be the reason a check is skipped, and the business check behind a non-displayed field runs anyway. <!-- rule: hidden-field-not-validation -->
- **[P2]** Selecting screen fields to change — prefer `screen-name = 'FIELD'` for one field or `screen-group1 = 'GRP'` for a group; a plain substring match on `screen-name` (e.g. a range over a `MATNR`-like set) is fragile — set explicit groups in the Screen Painter for blocks you toggle together. Reversing a change on the next `LOOP AT SCREEN` without `MODIFY SCREEN` has no effect — each attribute change must be followed by `MODIFY SCREEN` to be applied.
- **[P3]** **does not exist:** a `REQUIRED` addition on `FIELD`/`CHAIN` in the flow logic (`FIELD` takes only `MODULE` and `WITH`) — a required-field check is a `MODULE` with `MESSAGE TYPE 'E'`; for a *dynamic* (condition-dependent) requirement use `screen-required = 1` in PBO.
- **[P2]** The OK-code field name belongs to the dynpro, not to `SET PF-STATUS` (see the `ok_code` rule above).
- **[P3]** `SET CURSOR FIELD f` (place the cursor) / `SET CURSOR LINE n` — to direct focus (e.g. back to the offending field after a check); combine with `MESSAGE ... TYPE 'E'` so the message and the cursor point to the same field. Do not invent focus control values.
- **[P1]** Confirmation before an irreversible action (delete/archive/overwrite) — the standard dialog FM `POPUP_TO_CONFIRM` (question text passed in, the answer returned in an `IMPORTING` parameter; the siblings `POPUP_TO_CONFIRM_STEP`, `POPUP_TO_CONFIRM_LOSS_OF_DATA`, and `POPUP_TO_DECIDE`/`POPUP_TO_DECIDE_LIST` for a choice). Do not build your own popup screen or `CALL SCREEN` for a yes/no question, and do not re-invent the "really?" text. Every non-"continue/yes" answer (`no`, `cancel`, an empty answer, a `sy-subrc <> 0`) is a refusal — return to the caller without the write; an unchecked answer is a deleted record. <!-- rule: confirm-irreversible-action -->
- **[P3]** Do not transport values from screen to program with implicit work areas — use the field with an explicit `TYPE` (see `data.md`, no `TABLES`); the dynpro field and the ABAP variable are the same name by convention, not by the work-area mechanism.

> Sources: SAP Help "Input Checks in Dialog Modules" (CHAIN/FIELD/MODULE, ON CHAIN-INPUT, message handling), ABAPDocu "Dynpro".
