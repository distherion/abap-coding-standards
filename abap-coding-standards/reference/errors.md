# Error handling

> Class-based exceptions, checking results, the SAP LUW (`COMMIT`/`ROLLBACK`), `ENQUEUE`/`DEQUEUE`, resumable exceptions.
> Related: `luw.md` (the update task, V1/V2, `CALL FUNCTION ... IN UPDATE TASK`), `logging.md` (messages and the Application Log), `hr-pa-write.md`/`hr-pd-write.md` (the trial/lock rules these frameworks add), `parallel.md` (LUW per task, bgRFC), `integration.md` (the commit a remote call performs, its predefined RFC exceptions).

- **[P2]** Class-based exceptions (`CX_*`), not classic `RAISE`.
- **[P1]** Do not catch a broad `CATCH cx_root`/`cx_sy_*`-base — it swallows everything, including `CX_NO_CHECK`/system ones. Catch a concrete `zcx_*`/`cx_*` and wrap it (see below); if `CATCH cx_root` is unavoidable — re-raise or log, do not swallow. <!-- rule: no-broad-catch -->
- **[info]** "No data" has no single contract — match the API instead of unifying it: the BL read and the HRPAYFI posting read disagree on what "nothing found" means (`hr-pa.md`, `hrpa-bl-read-empty`; `hr-payroll.md`).
- **[P3]** One base exception class per package; raise one type; subclasses — only so the caller can distinguish cases.
- **[P2]** Exceptions — for errors, not for regular cases (Clean ABAP): a valid, expected outcome is a regular result (`RETURNING` value/status), not an exception — otherwise call sites are noisy and the real results are hidden. Do not model expected cases (a toggle, "already exists", optional "not found") as exceptions where the caller is supposed to handle them as normal.
- **[P2]** abapGit: an exception class (descendant of `CX_*`) in `.clas.xml` requires `<CATEGORY>40</CATEGORY>` (a normal class — 0); without it, it is created as a normal class (activation does not fail).
- **[P0]** Unrecoverable — cannot continue: stop processing and do not commit. Mechanism — by application type: `RAISE` up to the top level (there → message/HTTP 500), or log + abort. "Swallowed and moved on" — not allowed. <!-- rule: unrecoverable-no-commit -->
- **[P1]** Do not use `ASSERT` for business/invariant checks: it aborts the program with a dump, is meant for assumptions (and even with `ID`/`FIELDS` a *violated* assertion still aborts), and active assertions cannot be handled/relogged like class-based exceptions. Integrity/impossible-state checks — only `IF … RAISE` with a clear text, or explicit error handling. (Only `ASSERT … ID` can be deactivated via a checkpoint group / SAAB — an `ASSERT` without `ID` is always active and cannot be switched off.) <!-- rule: no-assert-for-business -->
- **[P2]** No `BREAK-POINT` in transported code — a debug leftover, not a checkpoint: in the user's dialog session the program stops in the debugger and the session stays blocked until someone continues, and a plain `BREAK-POINT` is always active — it cannot be switched off from outside the source. A switchable breakpoint is the checkpoint form (`BREAK-POINT ID grp`/`LOG-POINT ID grp` with the group maintained in SAAB), and debugging your own session is done with an external breakpoint, not by editing the source. Same class of leftover as the `ASSERT` above — remove it before transport.
- **[info]** `RAISE EXCEPTION NEW ...` — from 7.52 only, NOT in 7.50 (see `style.md`, "Version").
- **[info]** `MESSAGE ID sy-msgid TYPE sy-msgty NUMBER sy-msgno WITH ...` (dynamic message) requires the exception class to implement `IF_T100_DYN_MSG`; a static `MESSAGE eNNN(class)` needs only `IF_T100_MESSAGE`. `WITH` fills `msgv1..4` only with `IF_T100_DYN_MSG`. To move an `IF_T100` exception's message into `sy-msg*` — `cl_message_helper=>set_msg_vars_for_if_t100_msg( text = lx_exc )` (the importing parameter is `text`, not `io_exception` — a named `io_exception` does not compile; a positional `set_msg_vars_for_if_t100_msg( lx_exc )` also works).
- **[info]** Exception class constructor: `previous TYPE REF TO cx_root OPTIONAL` (copy the signature only into a `CX_ROOT` descendant; the `!` before a parameter is cosmetic — do not write it by hand).
- **[P2]** Wrap others' exceptions (`cx_reca_symsg` and other `cx_*` of external components) in your own `zcx_*` — do not let them leak into your code.
- **[P3]** Handle an exception as close as possible to where it is raised — at the level whose context already has enough information. Neither propagate deeper than needed nor catch early without a purpose: an early catch followed by a re-raise is noise, an early catch that swallows is a defect (see the empty-catch rule below).
- **[P2]** Fail fast: check preconditions at the start of the method.
- **[P2]** Write under a lock: `ENQUEUE_*` (enqueue server, not a DB lock) + check (`foreign_lock`); `DEQUEUE_*` at the end, in all branches, including `CLEANUP`. Generated `ENQUEUE_*` FMs take the parameters `_scope` (lock scope), `_wait` (block on a foreign lock instead of returning `foreign_lock`) and `_collect` (collect-mode locking).
- **[P2]** HR PA writes — through the dispatcher FM, never a direct `pa000x` write: which entry point and how it routes per infotype — `hr-pa-write-dispatch.md` (`hr-write-dispatch`); the class layer behind it, its trial and locks — `hr-pa-write.md` (`hrpa-bl-trial`, `hrpa-bl-trial-close`); the PD write trial — `hr-pd-write.md` (`pd-write-via-object-layer`).
- **[P1]** Check the result of a call with a status (`sy-subrc`, an HR FM's return structure, `et_message`, `ev_success`) immediately, before other calls/assignments: the next call overwrites the previous result → an error looks like success. Do not consider an operation successful until all checks pass. Good: `CALL FUNCTION 'FM' ... . IF sy-subrc <> 0. ... RETURN. ENDIF.` Bad: another statement (`CLEAR`, a second call) between the call and the `IF sy-subrc`. <!-- rule: check-subrc-immediately -->
- **[P2]** A legacy FM call site adds to the check above (`check-subrc-immediately`): handle the declared classic `EXCEPTIONS ...` (a non-handled `subrc` is a **silent** failure, not an automatic error); a blanket `EXCEPTIONS OTHERS = n` that discards every exception is the classic-FM analog of an empty `CATCH` — handle the named exceptions, do not swallow `OTHERS` blindly. `TABLES` parameters of a classic FM are passed **by reference** — the FM can modify the caller's table without declaring it; copy the table at the call site if it must not change. Wrap legacy FM calls in a class method so the check and the error handling are in one place (see `classes.md`).
- **[P1]** `CHECK` outside a loop ends the current procedure silently: the condition is false → the procedure returns right there, with no message and no exception — the caller sees a normal return. On a read path that is "no data" read as success; on a write path everything after the `CHECK` — the validation, the write itself, the commit — is skipped without a trace. `CHECK sy-subrc = 0.` is the same exit keyed on the previous statement's result (the code below it may never run). Write the guard explicitly — `IF ... RETURN`/`RAISE` — so the skipped work is visible at the call site. `CHECK` **inside** a `LOOP` stays legitimate loop control (`classes.md`). <!-- rule: check-subrc-silent-exit -->
- **[P2]** `SUBMIT ... AND RETURN` returns no result/error, `sy-subrc` after `SUBMIT` is unreliable: do not consider an operation successful from the `SUBMIT` return. Check the fact of the write afterwards (`READ`/`SELECT`) or use an FM/class with an explicit status.
- **[P2]** One logical operation = one `COMMIT WORK` at the end, after all checks. COMMIT "in chunks" — only in mass loading: independent records of the same kind, each chunk self-consistent (records, log rows, a table filled from a file). A loop over a **business object** — a header with its items, a document with its rows, a payment with its allocations — is not that: one `COMMIT` per iteration splits the LUW and an interruption leaves the object half-saved while the code reads as a single transaction (SKILL.md, "Exception to downgrade"). `BAPI_TRANSACTION_COMMIT`/`BAPI_TRANSACTION_ROLLBACK` are the BAPI-layer equivalents — `BAPI_TRANSACTION_COMMIT` ≈ `COMMIT WORK AND WAIT` **only with `WAIT = 'X'`** (the FM then defers the return until the V1 update of the LUW is complete); without `WAIT = 'X'` it behaves like plain `COMMIT WORK` — do not read back the written data or notify until the update has actually finished.
- **[P1]** `WAIT UP TO n SECONDS` is not a plain sleep: it switches the work process, and a work process carries one database LUW — the statement therefore performs an **implicit database commit** (ABAPDocu: "each time the WAIT statement is used, a database commit is performed") and must not be used between statements that open or close a DB cursor. Inside one logical operation it splits the LUW exactly like an extra `COMMIT`: an interruption leaves a half-saved state (a header without its items) while the code reads as a single transaction. A pause that must not commit — `ENQUE_SLEEP` (keeps the work process, no commit); waiting for a result — `COMMIT WORK AND WAIT`/`BAPI_TRANSACTION_COMMIT` with `WAIT = 'X'`, not a sleep. <!-- rule: wait-up-to-implicit-commit -->
- **[P2]** User messages — only via message class SE91 (class/number as literals — otherwise where-used in SE91 disappears) or text elements `TEXT-xxx`; not a literal. Message parameters — `&1..&4`.
- **[info]** If message attributes are passed implicitly (variables `sy-msgid`/`sy-msgno`/…, e.g. from an exception), keep a static anchor so the message stays in the where-used list: `IF 1 = 2. MESSAGE e123(abc) INTO sy-msgli. ENDIF.` (class/number as literals, see above) — then the message class/number is discoverable from SE91.
- **[P2]** `MESSAGE ... INTO data(x)` displays nothing and does not evaluate the message type — it copies the message text and fills `sy-msgid`/`sy-msgty`/`sy-msgno`/`sy-msgv1..4`; that is the documented way to move a message into your own log or exception (`logging.md`), not a way to show it to the user. And do not rely on a `MESSAGE` to stop the logic of a procedure: what happens after it depends on the type **and** the context (`E`/`A` end the processing block — an event block returns to the program call, a PAI module to the screen, a selection screen to the selection screen; `I`/`S`/`W` continue right after the statement; `X` dumps), so `MESSAGE eNNN` inside a method is not a substitute for `RAISE`/an error result — the caller receives no signal that it must stop.
- **[P1]** An empty `CATCH` (immediately `ENDTRY`) is forbidden — swallowing an error: handle the exception or do not catch at all. <!-- rule: empty-catch-forbidden -->
- **[P1]** A non-empty `CATCH` that turns the error into an ordinary result — a `CLEAR`ed table, `abap_false`, an initial structure — is the same defect as an empty one (`empty-catch-forbidden`), just harder to see: the code below the catch reads the outcome as a legitimate "no data"/"no changes", and on a write path that verdict is what drives the write. Scenario: a read fails (an authorization denial, a framework error), the catch clears the result table, the caller concludes "no such record/relation" and creates one. Wrap the exception into your own `zcx_*` and hand it up (an error `RETURNING` object, a status the caller must check), or handle it where the context can act on it — `check-subrc-immediately` is the status-based twin of this rule. <!-- rule: catch-into-default -->
- **[P1]** A `CATCH` can catch nothing when the exception crosses a function-module boundary: a class-based exception of category `CX_STATIC_CHECK`/`CX_DYNAMIC_CHECK` must be declared in the interface of every procedure it leaves, and the framework FMs that raise `cx_hrpa_*` declare no exception class at all (`HR_CONTROL_INFTY_OPERATION`, `HR_INFOTYPE_OPERATION`, `HR_MAINTAIN_MASTERDATA`). An undeclared checked exception leaving such an FM is an interface violation: the runtime raises `CX_SY_NO_HANDLER` **at the call site** with the original exception in `PREVIOUS`, so a `TRY ... CATCH cx_hrpa_violated_assertion` around that `CALL FUNCTION` never fires, and uncaught the short dump names the **original** exception, not the wrapper. `CX_NO_CHECK` and its subclasses — `CX_SY_NO_HANDLER` among them — cross any interface. Fix, one of: declare the class in the callee's interface (an FM exception class in the Function Builder, `RAISING` in a method); catch `cx_sy_no_handler` and unwrap `PREVIOUS` (the T100 key sits on the original, not on the wrapper); or pre-validate with a class method that declares its exceptions in its own signature — `CL_HRPA_INFOTYPE_CONTAINER=>ASSERT_SECONDARY_INFTY` raises `CX_HRPA_VIOLATED_ASSERTION` and can be called before the write. The same holds for any FM whose implementation may raise an undeclared checked exception. <!-- rule: fm-boundary-hides-exception -->

# Resumable exceptions

- **[info]** `RAISE RESUMABLE EXCEPTION ...` — the caller can `CATCH ... BEFORE UNWIND` and continue via `RESUME` (execution continues *after* the `RAISE`). A method that may raise a resumable exception declares it in the signature as `RAISING RESUMABLE( zcx_... )` (distinct from the `RAISE RESUMABLE EXCEPTION` statement). `RETRY` — allowed in a normal `CATCH`: re-runs the whole `TRY` block from the start. Do not confuse them: `RETRY` repeats the block, `RESUME` continues after `RAISE` (and requires `BEFORE UNWIND`).
- **[P3]** Resumable — for "try again/substitute a value", not for normal errors: a normal error — a normal exception.
- **[P2]** `CATCH ... BEFORE UNWIND` is more expensive than a normal `CATCH` (does not unwind the stack, keeps context) — use deliberately, not by default.
