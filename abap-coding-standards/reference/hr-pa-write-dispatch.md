# HR — PA write: NITF or OITF

> Release: 7.50. The dispatch lives in the function group HRMM (`HR_CONTROL_INFTY_OPERATION`); behind it sit the class framework (`cl_hrpa_masterdata_bl` — the new infotype framework, NITF) and the PA module pool SAPFP50P (the old one, OITF).
> Which entry point a PA write takes, what decides NITF vs OITF, and what each branch costs in LUW, lock and authorization. The class branch in detail — `hr-pa-write.md`; framework entry points and the read side — `hr-pa.md`; authorization — `security.md`.

## Entry point

- **[P1]** Write PA infotypes through `HR_CONTROL_INFTY_OPERATION`, not through `cl_hrpa_masterdata_bl` directly: only the dispatcher applies the NITF/OITF decision, so a class-path write of an infotype that customizing gives to the old framework is stored with the classic checks skipped, and nothing reports it. <!-- rule: hr-write-dispatch -->
  - **What breaks:** IT2001 is old-framework by definition — `infotype_admissible_for_newitf` (function group `HRMM`) answers "not admissible" for 0000/0001/0003/0031 and every `2xxx` before it reads a single customizing row; the time-binding check of an absence (`ZEITB`) and every project check class behind it live in the module pool, so an absence the dialog rejects goes in through the class path. The class path has no infotype guard at all: `cl_hrpa_masterdata_factory=>get_business_logic( )` reads no customizing — it raises `cx_hrpa_violated_precondition` only when the factory was put into legacy mode (`cl_hrpa_masterdata_factory`), which the module pool `FP50PE11` does only while the CE masterswitch is off — and hands back a working BL for `NITF_ADM = 0` just the same.
  - **Fix:** `CALL FUNCTION 'HR_CONTROL_INFTY_OPERATION' EXPORTING infty number subtype objectid lockindicator validitybegin validityend recordnumber record operation tclas IMPORTING return key` — `tclas = cl_hrpa_tclas=>tclas_employee` (`'A'` is only the default of the FM), `operation` — the PSPAR action `'INS'`/`'MOD'`/`'DEL'`/`'COP'` (`if_hrpa_constants`; the same constants in the `HRMM` top include), `record` — the `Pnnnn` built by `cl_hr_pnnnn_type_cast=>prelp_to_pnnnn`. The class path stays for the infotypes it is admissible for (`hr-write-path-by-infotype`).
  - The answer is a `bapireturn1`: an error is `return-type CA 'EA'` and the parameters sit in `return-message_v1..4` (`BALW_BAPIRETURN_GET1` fills them — `sy-msgv*` may hold a leftover from something else). `key-recordnr` is the SEQNR the framework assigned — needed to address the same record again (text cluster, `itxex`). `dialog_mode` (default `'0'`) takes no screens; a screen run is the dialog transaction, not an interface.

- **[P1]** NITF or OITF follows from the infotype, `T582ITVCLAS`, `T582ITD` and the CE masterswitch together — never from `NITF_ADM` alone. <!-- rule: hr-write-path-by-infotype -->
  - Order of the decision (`infotype_admissible_for_newitf` and the check-class logic behind it, function group `HRMM`): employee tclas only (applicants never take NITF); 0000/0001/0003/0031 and `2xxx` → OITF, unconditionally; no `T582ITVCLAS` row → OITF; `NITF_ADM = '1'` → NITF; `'3'` → NITF, and the masterswitch check is skipped (completely decoupled); `'2'` → NITF **only** if a `T582ITD` row exists for INFTY + MOLGA of the pernr; and for everything left `cl_hrce_masterswitches=>infotype_framework_is_active = false` → OITF.
  - Read it with `cl_hr_t582itvclas=>read( infty )` / `cl_hr_t582itd=>read( infty molga )` (both buffered; an empty result means "no row"); MOLGA the way the framework reads it — `HR_COUNTRYGROUPING_GET( pernr tclas begda endda → molga )` (the FM the dispatcher itself calls), class alternative `cl_hrpa_molga=>read_molga_by_pernr( )` (`hr-pa.md`).
  - **What breaks:** `NITF_ADM = '2'` is the value that reads as "admissible" — with no `T582ITD` row for that MOLGA the infotype is old-framework, and the class write goes through without its checks; an infotype that has no `T582ITVCLAS` row at all (older or customer infotypes) is old-framework by that rule and the class path writes it anyway.

- **[P1]** On the dispatcher path you lock and you carry the authorization: `HR_INFOTYPE_OPERATION` calls `HR_MAINTAIN_MASTERDATA` with `NO_ENQUEUE = 'X'` and the module pool dequeues at the end only when `NO_ENQUEUE` is initial — with `'X'` nobody locks the pernr for you. There is no `no_auth_check` and no `massn`/`massg` on this FM either: the authorization is checked inside, and the classic path takes action and reason from the record (module `SET_PSPAR` of the module pool `MP000030` — "supplies PSPAR-MASSN by P0000-MASSN"). <!-- rule: hr-write-dispatch-lock -->
  - **Fix:** `cl_hrpa_masterdata_enq_deq=>enqueue_by_pernr( )` + `dequeue_by_pernr( )` around each record (`hr-pa-write.md`), and make sure the technical/RFC user holds HR authorizations for every infotype it writes — a call that leans on `no_auth_check` in a copy of the class path fails here (`security.md`). One call is one LUW (below), so take the lock per record, not once for a batch.

- **[P1]** `HR_CONTROL_INFTY_OPERATION` is one LUW per call, not per group: with `nocommit` unset it commits inside the call — `LUW_MODE = '1'` → `put_infotyp_buffer_commit` + `COMMIT WORK` in `HR_MAINTAIN_MASTERDATA`, or the NITF branch's `flush( no_commit = space )` — and on an error it rolls back and re-initializes the P-buffer as part of the call. `nocommit = 'X'` → `'0'`: nothing is flushed, the caller commits **and** the caller cleans the buffer; the check-only operation (`'CHK'`) → `'3'`: the checks run, the buffer is initialized, nothing is written. <!-- rule: hr-write-dispatch-luw -->
  - **What breaks:** a payload written one call per record is that many LUWs — the third record failing leaves the first two committed while the run reports a failure; and deciding `INS`/`MOD` by an exact-key database read collapses legal parallel records (two `IT0015` for one day differ only in `LGART`): the second one `MOD`s the first instead of adding a record.
  - **A group as one LUW:** `nocommit = 'X'` on every record, then finish once — class branch `cl_hrpa_masterdata_bl~flush( no_commit = abap_true )` (registers the buffer in the update task, does not commit), then a single `COMMIT WORK AND WAIT`. The class handle for that flush is exported by the dispatcher itself — `REFERENCE(MASTERDATA_BL) TYPE REF TO IF_HRPA_MASTERDATA_BL` of `HR_CONTROL_INFTY_OPERATION`, no second `get_instance( )`. Both branches land in that one update task, so even a mixed group (business trip 9301 + `IT2001`) is one LUW. The caller then owns the cleanup the FM skipped on error: `ROLLBACK WORK`, `HR_PSBUFFER_INITIALIZE` (the P-buffer the module pool left behind) and the class buffer's `initialize( )`.
  - **`INS`/`MOD` comes from the payload's `PSKEY-SEQNR`:** initial → `if_hrpa_constants=>gc_infotype_operation_insert`, the framework assigns the record number (`key-recordnr` of the answer); non-initial → `gc_infotype_operation_modify` with that `recordnumber`, and `PSHD1` carried over from the record read *by the full pskey* (`if_hrpa_plain_infotype_access~read_by_pskey`; `cl_hrpa_read_infotype=>read_single` has no `seqnr` parameter) — otherwise `MOD` wipes the grouping value (`hr-pa-write.md`, `hrpa-container-modify-from-buffer`).
