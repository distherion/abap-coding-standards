# HR — PA write path

> Release: the 7.50 API of the PA framework (`cl_hrpa_*`). The ordinary entry is the dispatcher — `hr-pa-write-dispatch.md`; the read side and the framework entry points — `hr-pa.md`.
> Writing PA master data: trial/flush, containers, locks, messages, and everything a write pulls in (time constraints, OM sync, retrocalc, BAdI checks) — plus, in the last section, the APIs for a BL you drive yourself.

## Write path — trial and container

- **[P1]** One class-BL data call is one trial, and the framework opens and closes it itself: `if_hrpa_masterdata_bl` — `insert`/`modify`/`delete`/`action`/`regroup` run `start_trial` → the infotype logic → `assert_matching_error_states( message_list = ... is_ok = ... )`, then `CLEANUP. discard_trial( magic_cookie )`, then `approve_trial`/`discard_trial` by `is_ok`, then `message_list->add_messages( message_handler )`. Write a wrapping trial yourself only when you drive the BL by hand for several records (`get_infty_container` → `modify_primary_record` → `insert`/`modify`): `start_trial( IMPORTING magic_cookie TYPE REF TO if_hrpa_token )`, closed by `approve_trial( magic_cookie )`/`discard_trial( magic_cookie )` on every path — the same contract as in PD (`hr-pd-write.md`, `pd-dispatch-bl-autotrial`). `flush` is never the framework's job: `flush( no_commit = abap_false )` is the one `COMMIT WORK` for the group, `abap_true` only registers the buffer in the update task. `read`/`get_infty_container` do not trial. <!-- rule: hrpa-bl-trial -->

- **[P1]** A trial **you** started must be closed on every path, including a failed `flush`: a skipped `discard_trial` leaves a level on the write-buffer stack and every later `flush` fails with `cx_hrpa_invalid_buffer_stack` (`stack_not_empty`) for the rest of the session. After `approve_trial` the cookie is consumed — resetting that path means `initialize( )` (it also drops the read buffer and pending OM data). The PD layer does the same under its own names: `if_hrbas_dispatch_bl~flush` raises `cx_hrbas_invalid_buffer_stack` with `textid = cx_hrbas_invalid_buffer_stack=>cx_hrbas_stack_not_empty` while the cookie stack is not empty, and the PD admin `flush( )` does **not** close a trial — it only delegates to the dispatch BL, so `flush` before `approve_trial`/`discard_trial` fails. <!-- rule: hrpa-bl-trial-close -->

- **[P1]** PA container write path — a container handed to `if_hrpa_masterdata_bl~modify` must be the one **read from the buffer**, never one built from your own payload. <!-- rule: hrpa-container-modify-from-buffer -->
  - **What breaks:** `cl_hrpa_data_sharing~modify` compares `container->grouping_value( )` with `old_container->grouping_value( )` after the ALE check and raises `cx_hrpa_invalid_parameter` (`parameter = 'CONTAINER'`) on any difference (`cl_hrpa_data_sharing~modify`; the identical check after the time-constraint step). The standard comment says it outright: "A container which is to be modified must be read from the buffer. It must not be created. Newly created containers can only be inserted."
  - **Why a hand-built record loses the value:** `grouping_value( )` is `a_pshd1-grpvl`, and `if_hrpa_infty_container_data~modify_primary_record` takes the **whole PSHD1 from the passed record**, preserving only `itxex`/`refex`. A record built outside PA (`cl_hr_pnnnn_type_cast=>prelp_to_pnnnn` over a `PRELP` without `GRPVL`; `GRPVL` lives in `PRELP`/`PSHD1` and in the `paxxxx` tables) therefore wipes the grouping value — `modify` of an existing key fails, while `insert` passes: a new key gets it from the framework (`set_grouping_value( a_grouping_reader->c_gpval_ungrouped )`) and has no old container to compare against.
  - **Fix:** carry the header over before `modify_primary_record` — `ASSIGN <ls_pnnnn> TO <ls_pshdr> TYPE pshdr CASTING.` then `<ls_pshdr>-pshd1 = lo_old->pshd1( ).` (the `PSHD1` getter sits on `if_hrpa_infty_container`, aliased in `cl_hrpa_infotype_container`; the framework casts `pnnnn` to `pshdr` itself) — or `set_grouping_value( old_container->grouping_value( ) )` (`if_hrpa_infty_container_group`).
  - **Catch the standard ancestor:** `cx_hrpa_invalid_parameter` → `cx_hrpa_violated_precondition` → `cx_hrpa_violated_assertion` → `cx_dynamic_check`, so a `CATCH` listing only your own wrapper class (a subclass) catches nothing, and the session ends in `UNCAUGHT_EXCEPTION`.


## Locks and messages

- **[P2]** Locks — `cl_hrpa_masterdata_enq_deq` (static) `enqueue_by_pernr( EXPORTING tclas = cl_hrpa_tclas=>tclas_employee pernr message_handler IMPORTING is_ok locking_user )` / `dequeue_by_pernr( EXPORTING tclas pernr )`. Asymmetric: only enqueue returns a status and fills the handler — every `is_ok = false` branch writes an E message (e.g. `PBAS_SERVICE 014` with the locking user), so the row error comes from the handler, not from `sy-msg*`; `dequeue_by_pernr` declares neither `is_ok` nor `message_handler`, a failed unlock shows only as a `CATCH`. Enqueue also locks the connected objects (the CP and the pernrs of 0322/0021) and registers in `HR_DEQUEUE_REGISTER` — not a cheap one-object lock. Both raise `cx_hrpa_violated_assertion` (incl. `cx_hrpa_invalid_parameter` for `pernr = '0'`, `cx_hrpa_missing_lock` when promoting a lock not requested as promotable).
  - **Not with the legacy pernr locks** — `HR_EMPLOYEE_ENQUEUE`/`HR_EMPLOYEE_DEQUEUE` and their BAPI twins `BAPI_EMPLOYEE_ENQUEUE`/`BAPI_EMPLOYEE_DEQUEUE`: the same lock object sits behind both (`ENQUEUE_EPPRELE`), but a different request — the FM locks **immediately** with a hard-coded `_scope = '3'` and passes neither `mode_prel` nor `_collect`/`_wait` (function group `1065`), while the class hands over `enq_scope`/`enq_wait`/`enq_collect` (defaults `'2'`/`' '/`'X'` — a local collect, written at flush), dequeues with `_collect = true` (`cl_hrpa_masterdata_enq_deq`) and keeps its own enqueue table of the pernrs and the CP that `dequeue_by_pernr`/`dequeue_all` release exactly. A pernr locked through the FM is not in that set, so a framework write under it runs under a lock the framework neither requested nor releases — and the BAPI-style `return`/`locking_user` of the FM is not the `is_ok` + E-message contract of the handler (`errors.md`).

- **[P2]** HR messages — `cl_hrpa_message_list` (instantiate with `NEW`, no factory — unlike `cf_reca_message_list=>create`), producer interface `if_hrpa_message_handler`. `get_message_list`/`get_error_list`/`get_abend_list`/`has_error`/`has_abend`/`add_messages` are all declared `RAISING cx_hrpa_violated_assertion` — keep every call inside a `TRY`. Same accumulate/query pattern as `cl_reca_message_list` — `logging.md`; row error by type — `get_error_list` (`msgty = 'E'`), then `get_abend_list` (`'A'`; `is_ok = false` may carry either), `get_message_list` — everything. Where the messages are deliberately not needed, the framework accepts `cl_hrpa_dummy_message_handler` (`create public`, `add_message` empty) instead of the real list — pass it knowingly: it discards every message.

## Around a write

- **[P2]** PA↔other objects on write — do not build your own sync and do not trigger the standard integrations yourself: the framework runs them (the OM integration on the write/publish path as `post_flush`, the ALE change pointers), and on the dispatcher path the outcome reaches you as `bapireturn1` (`hr-pa-write-dispatch.md`). Hooks to switch an integration off or to drive one by hand — "Class path only" below.

- **[P2]** A broken framework precondition/postcondition (`cx_hrpa_violated_assertion` and its descendants) — `cl_hrpa_resolve_exception=>resolve( exception message_handler )` at the boundary instead of letting it leak into the caller or swallowing it (`errors.md`).

- **[P1]** HR writes and time constraints (PA infotypes 0000/0001/0002/…): a change is not a blind `UPDATE` of `pa000x` — the time-constraint logic decides how a new begin/end date inserts, delimits or overwrites existing records. TC1 — a single uninterrupted record (no gaps, no overlapping); TC2 — at most one record with gaps allowed (no overlapping); TC3 — several parallel records delimited by dates. Route the write through the dispatcher and the framework's own trial (`hr-pa-write-dispatch.md`, `hr-write-dispatch`) with a pernr lock (see `errors.md`), never `MODIFY pa0001` — otherwise the record history gets gaps/overlaps (a P1 data-consistency defect, not just style). <!-- rule: hr-writes-time-constraints -->

- **[P3]** Do not copy ABAP-derived HR values (seniority, age, dated differences) into a PA infotype at runtime — they are recomputable from the master records; storing derived data that can drift from the source is a data-quality find.

- **[P2]** Your own checks for an infotype go through the BAdI, not by copying the standard class: `if_ex_hrpad00inftybl` / `if_ex_hrpad00inftydb` (BAdIs `HRPAD00INFTYBL`/`HRPAD00INFTYDB`) — `initialize( infotype_read_handler masterdata_buffer_handler molga_read_handler timeconstraint_handler masterdata_bl_handler … )` hands you the framework handlers, and the `*_computations` methods run **after** the standard checks (reference implementations: `cl_exm_im_hrpad00inftybl`, `cl_exm_im_hrpad00inftydb`). Check definitions for metadata — `cl_hrpa_foreign_key_check`.


## Class path only — driving the BL by hand

Not the ordinary path: the dispatcher hands you the class handle (the `MASTERDATA_BL` export) and reports through `bapireturn1`. Everything below is for a BL you hold and drive yourself (integration/BAdI context, several records in one trial).

- **[P2]** BL handle: the dispatcher's `MASTERDATA_BL` export (`hr-pa-write-dispatch.md`), or `cl_hrpa_masterdata_bl=>get_instance( )` / the factory's `get_business_logic( )` (`RAISING` — inside a `TRY`); methods — `if_hrpa_masterdata_bl` (`read`/`insert`/`modify`/`delete`/`action`/`get_infty_container`/`regroup`), `if_hrpa_buffer_control` (`start_trial`/`approve_trial`/`discard_trial`/`initialize`/`flush`). Container write: `get_infty_container( )` → check `is_ok` (a cleared container otherwise propagates) → `modify_primary_record( pnnnn )` (returns `IF_HRPA_INFTY_CONTAINER_DATA`, downcast `?=`) → `insert` / `modify( old_container = ... )`; a container is not created by class name — `cl_hrbas_infotype_factory` (`hr-pa.md`); `no_auth_check` — only where you verified authorization yourself (`security.md`).

- **[P2]** Handler — wrap the one you pass instead of post-processing the list by hand: `cl_hrpa_message_struct_remap` (implements `if_hrpa_message_handler`, `set_remapping( structure_name )`), `cl_hrpa_message_generic_remap`, `cl_hrpa_message_fields_remap`/`cl_hrpa_message_fields_preset`, detail-level filter `cl_hrpa_detail_messages` (`max_detail_level = 9`).

- **[P2]** Standard integrations — the framework runs them; to switch one off or to drive it by hand: `cl_hrpa_om_integration` (PA→OM), `cl_hrpa_bp_integration`, `cl_hrpa_ale_handler`/`cl_hrpa_dummy_ale_handler` (the dummy suppresses change pointers for technical writes), `cl_hrpa_workflow_handler`, `cl_hrpa_data_sharing=>trigger_regrouping( )`.
