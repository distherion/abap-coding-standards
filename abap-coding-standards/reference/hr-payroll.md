# HR — payroll and PT

> Release (7.50): payroll result reading, HRPAYFI, the PT request framework (`cl_pt_req_*`) and the RU localisation classes are standard 7.50 HR; the RU family is country-specific.
>
> Payroll result clusters and posting documents, PT request framework, RU localisation. PA master data — `hr-pa.md`, PD/OM object layer — `hr-pd.md`, general date arithmetic — `cl_reca_date` in `datetime.md`.

- **[P1]** Payroll result (PCL2) — read only via `PYXX_READ_PAYROLL_RESULT` (`clusterid`/`employeenumber`/`sequencenumber` → `payroll_result`), never the cluster by hand; fill `payroll_result-evp` from the chosen `RGDIR` row with `CORRESPONDING #( ls_rgdir )` (component names match on both sides, so the whole structure is written — the `MOVE-CORRESPONDING` form of an obsolete statement is not used here, see `data.md`). Choose that row deliberately — the requested period (`inper`/`fpper`) and the active one (`srtza = 'A'`) — and pass its `seqnr`: a `LOOP` that exits on the first row of an unfiltered `RGDIR` takes whichever period the read order happened to return, and every figure downstream is then another period's. A failed read is **not** "no money": `no_record_found`/`import_mismatch_error`/`versions_do_not_match`/`error_reading_archive`/`no_read_authority` answered with a bare `RETURN` leaves an empty result that downstream sums treat as zero — report the error instead. Contrast `hrpa-bl-read-empty` (`hr-pa.md`), where an empty read **is** the answer "no record". <!-- rule: payroll-result-read -->
- **[P1]** Never `IMPORT`/`EXPORT` the payroll clusters by hand: `IMPORT ... FROM DATABASE pcl2(ur) ID rx-key IGNORING STRUCTURE BOUNDARIES` maps the components by memory layout, not by name — as soon as the country structure gains a field the values land in the wrong components with no error, and the cluster-version/archive handling of the read FM is skipped too. Where a raw cluster access is genuinely needed, resolve the cluster id with `PYXX_GET_RELID_FROM_PERNR` and import `USING <pcl2_exp_imp>`. <!-- rule: payroll-no-hand-cluster -->
- **[info]** `RGDIR` (internal directory of payroll results) — the per-employee list of stored payroll results (in/off-cycle indicator, `seqnr`); `PYXX_READ_PAYROLL_RESULT` reads one by `seqnr` from it (above) into a **country-specific result structure** (e.g. `payRU_result` for Russia — the cluster name follows the national ISO convention). Always bind the payroll-result structure of the right convention (`molga`) the stored result expects. The directory itself is read with `CU_READ_RGDIR` / `CU_READ_RGDIR_NEW` (`persnr` → the `pc261`-typed result table) — not a hand-written `SELECT ... FROM pc261`; the row it returns is the `seqnr` for `PYXX_READ_PAYROLL_RESULT` and the source of its `evp` (above).
- **[P2]** The directory row is chosen, not looped for: the helpers pick by period instead of taking whichever row the read order returned — `CD_READ_LAST( begin_date = ... end_date = ... → out_seqnr )` gives the `seqnr` of the result covering the period (feed it to the read above), `CD_READ_PREVIOUS( in_record = <directory row> exact last all ignore_abkrs → TABLES out_rgdir )` the neighbouring one, `CD_READ_DATE_RANGE( begda = ... endda = ... → TABLES out_rgdir )` / `CD_READ_DATE_RANGE_ACTUAL_NV` (the same over an imported directory: `rgdir_in` → `rgdir_out`) the rows of the period. A hand-written `LOOP` that stops on the first/last row it sees is the same defect as reading the wrong period anywhere else — the figures downstream belong to another month.
- **[P2]** Wage-type data and its text — the customizing classes of the `cl_hr_t*` family (`hr-pa.md`), on the payroll tables too: valuation/attributes — `cl_hr_t512w=>read_at_date( molga = ... lgart = ... date = ... → t512w )` (buffered, keyed by the validity date, not by "today"), pay-scale group/level — `cl_hr_t510g=>read( )`. The wage-type **text** is the FM `HR_GET_LGART_TEXT( p_lgart = ... p_molga = ... → p_longtext/p_shorttext, EXCEPTIONS no_entry_in_512t )` — not `SELECT ... FROM t512t`. Both belong **outside** the per-pernr loop: a customizing read per row is the `SELECT`-in-loop of `open-sql.md`, and the text FM is not exempt from it.
- **[P2]** Payroll posting documents (HRPAYFI) report "nothing found" as an **exception** — `cx_hrpayfi_no_data_found` — not as an empty table (the HRPAYFI view layer, `cl_hrpayfi_mvc_view_salv_table`, is built around catching it). Catch exactly this class and treat it as the normal empty case; do **not** put `##NO_HANDLER` or an empty `CATCH` on it — the same read raises real errors too and a swallowed catch hides them. Note this is the **opposite** contract of `hrpa-bl-read-empty` (`hr-pa.md`): match the API, do not unify the two.
- **[P2]** PT requests (leave/absence requests — the PT request/approval framework) — only through the standard `cl_pt_req_*` layer, not by writing `pa2001`/`pa2002` yourself. Commands, statuses, roles and colours — from `cl_pt_req_const` (`c_cmd_prepare_modify`/`c_cmd_execute_send`/`c_cmd_execute_approve`/`c_cmd_execute_delete`, `c_reqstat_sent`, `c_item_ins`, `c_role_employee`, `c_actor_type_pernr`, `c_color_*`), never as your own literals; customizing and context — `cl_pt_req_customizing` (`get_modificators`, `get_team_settings`, `get_i0001_data`), `cl_pt_req_message_handler=>instance_get( )`, processor determination — `cl_pt_req_search_next_p`; the data structures are `pt_req_head`/`pt_req_request`/`pt_req_mode`.
- **[P2]** The Russian payroll result is the same read above, only the country part of it differs: from `PYXX_READ_PAYROLL_RESULT` or from the class layer on top of it — `cl_hr_pay_access->read_result( pernr molga period → pay_result_person pay_results )`, plus `initialize_buffer_from_tbuff( buffer = tbuff[] buffer_dir = buffer_dir[] )` when a whole person is read at once — you get a **country-generic** result object (`pay_results` is the `h99_hr_pay_result_tab` of `cl_hr_pay_result` refs, `pay_result_person` a `cl_hr_pay_result_person`). `->inter-rt` (the results table) is on the generic ref; the RU part needs a **checked** downcast — `CAST cl_hr_pay_result_ru( <result ref> )`, at person level `CAST cl_hr_pay_result_person_ru( <person ref> )` — and then `->natio-rures` (the RU rows: `lgart` and its sums), `->natio-rudat` (per-`cntr2` data, e.g. `lgtax`), `->molga`/`->person`. An incompatible cast is `CX_SY_MOVE_CAST_ERROR` — a dump, so cast a result you know belongs to this country (the `molga`/`relid` you asked for), not whichever row the loop holds. The scheme is the general one for every nationality — generic object plus the country class, never a hand-`IMPORT` of the country structure (`payroll-no-hand-cluster` above; the RU structure is `payru_result`); in the framework's BAdI signatures the same family arrives typed `cl_hr_pay_result_base`.
- **[P3]** RU localisation — `cl_hrpadru_date_tools` (`last_day_in_month( )`, `next_period( )`) and the wider standard family: `legal_properties`, `org`, `vacations`, `avr`, `fias`, `main_peras`, `it0294_factory` (infotype 0294), `log`/`log_ce`, `util`, `data_format`, `rh_struc`. Check this family before writing your own RU helper.
