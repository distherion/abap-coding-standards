# HR (PA / OM / payroll)

> HR master data, organizational management and payroll access. Authorization context — `security.md` (P_ORGIN, reader bypass), locks and trial pattern — `errors.md`, logical database — `ldb.md`.

- **[P2]** Read/change PA master data via the class framework (`cl_hrpa_*`), not via legacy FMs (`HR_READ_INFOTYPE`, `HR_INFOTYPE_OPERATION`) or direct `SELECT` from `pa0001…`. Entry point — `cl_hrpa_masterdata_factory`: `get_read_infotype( )` → `if_hrpa_read_infotype` (`read_single`), `get_business_logic( )` → `if_hrpa_masterdata_bl`, `get_masterdata_buffer( )`, `get_read_molga( )`, `get_read_timeconstraint( )`. The framework runs the authorization check and the buffer/trial logic itself; bypass only where you verified authorization yourself (`no_auth_check`, see `security.md`). Good: `cl_hrpa_masterdata_factory=>get_read_infotype( )->read_single( ... )`; bad: `HR_READ_INFOTYPE` / `SELECT ... FROM pa0001`.
- **[P2]** Write layer entry point — `cl_hrpa_masterdata_bl=>get_instance( IMPORTING masterdata_buffer OPTIONAL EXPORTING masterdata_bl TYPE REF TO if_hrpa_masterdata_bl )` (declared `RAISING cx_hrpa_violated_assertion` — call it inside a `TRY`); the factory equivalent is `get_business_logic( )` (same object; raises `cx_hrpa_violated_precondition` if the factory was initialized in legacy mode). Data methods (`if_hrpa_masterdata_bl`): `read` / `insert` / `modify` / `delete` / `action` / `get_infty_container` / `regroup`; buffer control (`if_hrpa_buffer_control`): `start_trial` / `approve_trial` / `discard_trial` / `initialize` / `flush`.
- **[P1]** PA write path — one group of records = one trial: `start_trial( IMPORTING magic_cookie TYPE REF TO if_hrpa_token )` → `read` / `get_infty_container` → `modify_primary_record` → `insert` / `modify`; on success `approve_trial( magic_cookie )` + `flush( no_commit = abap_false )`, on any failure `discard_trial( magic_cookie )` before returning. `flush( no_commit = abap_false )` commits the whole group with one `COMMIT WORK`; without `no_commit` the buffer is written without a commit — no partially written group, no per-record commits. <!-- rule: hrpa-bl-trial -->
- **[P1]** A started trial must be closed on **every** path, including a failed `flush`: a skipped `discard_trial` leaves a level on the write-buffer stack and every later `flush` fails with `cx_hrpa_invalid_buffer_stack` (`stack_not_empty`) for the rest of the session. After `approve_trial` the cookie is consumed — resetting that path means `initialize( )` (it also drops the read buffer and pending OM data). <!-- rule: hrpa-bl-trial-close -->
- **[P1]** `read` for a key with no record leaves `is_ok = abap_false` **and** adds no E/A message (the generic infotype BL exits via `CHECK` before setting `is_ok`): empty + no messages = "does not exist yet" (insert path), not a failure. Read into a fresh `cl_hrpa_message_list` and decide by `has_error( )`/`has_abend( )` — taking a bare `is_ok = false` for an error breaks every "not found → insert" case, and the framework's own postcondition (`assert_matching_error_states`: `is_ok = false` without an E/A message) raises `cx_hrpa_violated_postcondition`. <!-- rule: hrpa-bl-read-empty -->
- **[P2]** Locks — `cl_hrpa_masterdata_enq_deq` (static) `enqueue_by_pernr( EXPORTING tclas = cl_hrpa_tclas=>tclas_employee pernr message_handler IMPORTING is_ok locking_user )` / `dequeue_by_pernr( EXPORTING tclas pernr )`. Asymmetric: only enqueue returns a status and fills the handler — every `is_ok = false` branch writes an E message (e.g. `PBAS_SERVICE 014` with the locking user), so the row error comes from the handler, not from `sy-msg*`; `dequeue_by_pernr` declares neither `is_ok` nor `message_handler`, a failed unlock shows only as a `CATCH`. Enqueue also locks the connected objects (the CP and the pernrs of 0322/0021) and registers in `HR_DEQUEUE_REGISTER` — not a cheap one-object lock. Both raise `cx_hrpa_violated_assertion` (incl. `cx_hrpa_invalid_parameter` for `pernr = '0'`, `cx_hrpa_missing_lock` when promoting a lock not requested as promotable).
- **[P2]** `cl_hrpa_message_list` — `get_message_list` / `get_error_list` / `get_abend_list` / `has_error` / `has_abend` / `add_messages` are all declared `RAISING cx_hrpa_violated_assertion`: keep every call inside a `TRY`. Row error by type — `get_error_list` (`msgty = 'E'`), then `get_abend_list` (`'A'`; `is_ok = false` may carry either), `get_message_list` — everything.
- **[P2]** Container write: `get_infty_container( EXPORTING tclas pskey message_handler IMPORTING container is_ok )` — check `is_ok` (otherwise a cleared container propagates); the data goes in via `cl_hrpa_infotype_container->modify_primary_record( pnnnn )`, which returns `IF_HRPA_INFTY_CONTAINER_DATA` — downcast with `?=` (the specialized `cl_hrpa_it<nnnn>_container` inherit from `cl_hrpa_infotype_container`); the key of a freshly created container — `container->a_pskey`; then `insert` / `modify( old_container = <the container read by key> CHANGING container )`. `no_auth_check` — only where you verified authorization yourself (`security.md`).
- **[P2]** Framework exceptions `cx_hrpa_*`/`cx_hrbas_*` — `cx_hrpa_violated_assertion` is the root (`CX_DYNAMIC_CHECK`; `cx_hrpa_invalid_parameter`, `cx_hrpa_violated_precondition`, `cx_hrpa_violated_postcondition`, `cx_hrpa_missing_lock` derive from it, so one `CATCH cx_hrpa_violated_assertion` covers the whole write layer — `read`/`insert`/`modify`/`get_infty_container`/`flush`/trial/enqueue); also `cx_hrbas_violated_assertion`, `cx_hrpa_invalid_buffer_access`, `cx_hrpa_missing_authorization` — wrap in your own `zcx_*`, do not let them leak (`errors.md`).
- **[P2]** HR feature (tables T549B/T549C/T549D, texts T549T, transaction `PE03`) — `cl_hrpa_feature=>get_value( EXPORTING feature = <name TYPE t549d-namen> struc_content = <struct> IMPORTING return_value = <val> )` (classic FM fallback — `HR_FEATURE_BACKFIELD` with `feature`/`struc_content`). A decision table for many values — `get_table( feature = ... )`. Do not `SELECT` the feature decision by hand.
- **[P3]** TCLAS/OTYPE — constants, not literals: `cl_hrpa_tclas=>tclas_employee` (`'A'`), `=>tclas_applicant` (`'B'`), `=>otype_employee` (`'P'`), `=>otype_applicant` (`'AP'`); conversion `tclas_to_otype( )`/`otype_to_tclas( )`; validation `assert_admissible_tclas( )`/`assert_admissible_otype( )`.
- **[P2]** HR messages — `cl_hrpa_message_list` (instantiate with `NEW`, no factory — unlike `cf_reca_message_list=>create`), producer interface `if_hrpa_message_handler`. Same accumulate/query pattern as `cl_reca_message_list` — `logging.md` (`add_messages`, `has_error`/`has_abend`, `get_message_list`). Where the messages are deliberately not needed, the framework accepts `cl_hrpa_dummy_message_handler` (`create public`, `add_message` empty) instead of the real list — pass it knowingly: it discards every message.
- **[P2]** HR customizing table reads — the `cl_hr_t*` family (one class per table; in a single system ≥86 SAP classes of the family), `class-methods read( <key fields> ) RETURNING VALUE(<row>)`, buffered. `cl_hr_t001=>read( bukrs = ... )-butxt`, `cl_hr_t549a=>read( ... )`, `cl_hr_t591s=>read( ... )`, `cl_hr_t500p=>read( ... )`. Use it instead of a direct `SELECT` from `T001`/`T549A`/`T591S`/… — the class buffers and matches the table key. (If the landscape shows local `zcl_hr_t*` copies side-by-side with the standard family — that is duplication, prefer the standard classes.)
- **[P2]** OM/PD read — `RH_STRUC_GET` (`act_otype`/`act_objid`/`act_wegid`/`act_plvar`/`act_begda`/`act_endda` → `TABLES result_objec`) for a structure; `RH_READ_INFTY` (`infty`/`subty`/`begda`/`endda` → `TABLES innnn`/`objects`) for one object's infotype.
- **[P1]** PD write — only via the PD object layer, never `RH_INSERT_INFTY`/`RH_MODIFY_INFTY`/direct `HRP1000`/`HRP1001`: `cl_hrbas_pd_object_admin=>get_instance( )` → `start_trial( )` → the object methods → `approve_trial( )` + `flush( no_commit = abap_false )`, on error `discard_trial( )`. **The PD trial does not nest**: a second `start_trial( )` before the running one is closed hits `ASSERT … IS INITIAL. "No nesting possible` inside and **dumps** — close the trial on every path, including a failed `flush` (see `errors.md`, no-assert-for-business). `start_trial`/`approve_trial`/`discard_trial` take no parameters (the cookie is a class attribute, the caller does not get one); `flush` requires `no_commit` — no default. <!-- rule: pd-object-layer-trial -->
- **[P2]** PD object layer — instances: `create_object( otype short … → pd_object is_ok )`, `get_object_instance( otype objid … )`, `get_universal_object( otype realo … )`; `pd_object_classname` defaults to `cl_hrbas_pd_object` (own classes allowed) and the instances are cached in `cl_hrbas_pd_object_repository=>get_instance( )` (`get_object_instance`/`add_object_instance`/`remove_all_object_instances`). Lifecycle: `delete_object( )`, `change_object_validity( new_date mode … )` with `hrbas_validity_change_mode` (0 delimit / 1 extend / 2 new endda / 3 new begda; `adapt_infotypes` DEFAULT `'X'`); per-object buffer `initialize_buffer( )`/`initialize_buffer_for_object( )`/`update_buffer_for_object( )`. Locks: `set_exclusive_lock`/`set_optimistic_lock`/`set_shared_lock( … message_handler → is_ok )` + `remove_*_lock( )`, the optimistic one is meant to be promoted — `promote_lock_to_exclusive( )` / `is_optimistic_lock_promotable( )`; `enq_collect` default here is `' '` (the PA enqueue uses `'X'`). The admin methods return `is_ok` and declare no `RAISING` — `cx_hrbas_violated_assertion` comes from the instance methods below.
- **[P1]** PD instances — an initial `objid` is not validated and ends in a dump: `get_object_instance` asserts `objid IS NOT INITIAL` (`cl_hrbas_pd_object_admin.clas.abap:678`), and the `cl_hrbas_pd_object` constructor checks existence and asserts the result (`cl_hrbas_pd_object.clas.abap:700` `ASSERT is_ok = true.`, `:161` `ASSERT sy-subrc = 0.`) — an empty key gives an `ASSERT` dump (`ASSERTION_FAILED`), not `is_ok = false` and not a catchable exception (in the same export `create_object` checks only `otype`/`short`/`message_handler` — `cl_hrbas_pd_object_admin.clas.abap:472-474` — and inserts `p1000-objid = objid` as is). Check `otype`/`objid` (external objects — `realo`) before creating an instance; the same scheme sits in `ensure_call_consistence` (an initial `plvar`/`otype`/`objid` sets `is_consistent = false`, and the infotype methods then hit `ASSERT is_consistent = true` — `cl_hrbas_pd_object.clas.abap:339,369,408`). <!-- rule: pd-object-empty-objid -->
- **[P2]** `if_hrbas_pd_object` — the object instance (`a_objid`; via `if_hrbas_universal_object` also `a_plvar`/`a_otype`/`a_realo`/`a_is_external_object`, read-only). Infotypes: `read_infty( infty subty begda endda istat … → pnnnn_tab hrtnnnn_tab is_ok )`, `insert_infty`, `modify_infty( old_key … )`, `delete_infty( key … )`, `delimit_infty( old_key delimit_date … )` — the record goes in **`CHANGING pnnnn TYPE ANY`** (+ optional `hrtnnnn_tab`), i.e. the infotype logic edits the caller's structure in place. Relations: `get_relations` / `get_related_objects` / `create_relation` / `modify_relation( old_key … )` / `delete_relation( key )` / `delimit_relation( old_key delimit_date )`. Descriptions: `get_description` / `get_descriptions` / `insert_description` / `modify_description` / `get_general_description` / `insert_general_description` / `modify_general_description` / `delete_general_description`. Existence: `get_existence( → lowest_begda highest_endda all_existencies )` — the only method with the classic `EXCEPTIONS OBJECT_DOES_NOT_EXIST`. Common params `message_handler`/`no_auth_check`/`update_mode`, result `is_ok`, raises `cx_hrbas_violated_assertion`. `if_hrbas_universal_object` is the same read side (relations/descriptions/existence) for an object without a PD-object instance — external objects (`a_is_external_object`), for which `change_object_validity` must not be called.
- **[P2]** PD message handler — `if_hrbas_message_handler` (ref type `hrbas_msg_handler_if_ref`), **not** `if_hrpa_message_handler` of the PA layer; the concrete implementing class is not part of the export — verify in the system, do not assume `cl_hrpa_message_list` implements both. `update_mode` here is `hrbas_update_mode` (PA uses `hrpad_update_mode`).
- **[P2]** Payroll result (PCL2) — `PYXX_READ_PAYROLL_RESULT` (`clusterid`/`employeenumber`/`sequencenumber` → `payroll_result`); fill `payroll_result-evp` with `MOVE-CORRESPONDING` from the `RGDIR` row (`<ls_rgdir>-seqnr`). Do not read `PCL2` directly.
- **[P2]** PRELP↔infotype cast — `cl_hr_pnnnn_type_cast`: `prelp_to_pnnnn( )`/`pnnnn_to_prelp( )` (single), `prelp_to_pnnnn_tab( )`/`pnnnn_to_prelp_tab( )` (table), `wplog_to_pnnnn( )`/`pnnnn_to_wplog( )`, `view_to_prelp( )`/`prelp_to_view( )`. `PRELP` is the PA buffer record (`pernr`/`infty`/`subty`/`objps`/`sprps`/`endda`/`begda`/`seqnr`); `pnnnn` — the typed infotype structure. Do not cast by hand or `MOVE-CORRESPONDING` between them.
- **[P3]** Text/receipt clusters — `cl_hrpa_text_cluster` (PCL1) / `cl_hrpa_receipt_cluster` (PCL4).
- **[P3]** RU date tools — `cl_hrpadru_date_tools`: `last_day_in_month( )`, `next_period( )`. (General date arithmetic — `cl_reca_date` in `data.md`.)
- **[P1]** HR writes and time constraints (PA infotypes 0000/0001/0002/…): a change is not a blind `UPDATE` of `pa000x` — the time-constraint logic decides how a new begin/end date inserts, delimits or overwrites existing records. TC1 — a single uninterrupted record (no gaps, no overlapping); TC2 — at most one record with gaps allowed (no overlapping); TC3 — several parallel records delimited by dates. Route writes through the mastered framework / with the trial pattern and a lock (see `errors.md`), never `MODIFY pa0001` — otherwise the record history gets gaps/overlaps (a P1 data-consistency defect, not just style). <!-- rule: hr-writes-time-constraints -->
- **[P2]** Read an employee infotype for a **specific record** (e.g. by `begda` from a list) — prefer the framework `read_single` with the record key, not a `SELECT ... FROM pa0001 WHERE pernr = ... AND begda = ... AND endda = ...` filtered by hand; the framework applies auth + period logic and returns the exact record. `read_single` without a date returns the current/latest — pass the date when a historical record is intended.
- **[P3]** Do not copy ABAP-derived HR values (seniority, age, dated differences) into a PA infotype at runtime — they are recomputable from the master records; storing derived data that can drift from the source is a data-quality find (see `data.md`: SRVP containing redundancy).
- **[P2]** `PERNR`-level loops over a whole workforce — do not `SELECT` one `pa0001` row per `pernr`; retrieve the whole selection set in one read (the framework / a single bulk read) and group by `pernr`, then split the processing (see `open-sql.md`; `parallel.md` for bgRFC splits).
- **[info]** `RGDIR` (internal directory of payroll results) — the per-employee list of stored payroll results (cluster `PCL2`, in/off-cycle indicator, `seqnr`); `PYXX_READ_PAYROLL_RESULT` reads one by `seqnr` from it (above) into a **country-specific result structure** (e.g. `payRU_result` for Russia — the cluster name follows the national ISO convention). Do not read `PCL2` directly, and always bind the payroll-result structure of the right convention (`molga`) the stored result expects.
