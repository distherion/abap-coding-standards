# Logging

> Accumulate messages via the standard `cl_reca_message_list` → show → persist into the Application Log (SLG1).
- **[info]** `cl_reca_message_list` — a wrapper over the Application Log (SLG1). If the class is unavailable (not an RE-FX system) — the same mechanics via the standard BAL API: `BAL_LOG_CREATE`/`BAL_LOG_MSG_ADD`/`BAL_DB_SAVE`/`BAL_DSP_LOG_DISPLAY`. The principles (accumulate messages, do not stop on the first, show at the end) are the same.
- **[info]** Instance: `DATA(lo_msglist) = cf_reca_message_list=>create( id_object = ... id_subobject = ... id_extnumber = ... ).` — the factory (dominant pattern; returns `if_reca_message_list`, object/subobject set in one call). `cl_reca_message_list` is protected-instantiable — instantiate via the factory, not `NEW` (a subclass `zcl_bc_message_list` is fine as the project's wrapper). One per process — pass via parameters/DI; do not create your own Z-subclass or a singleton without need.
- **[P2]** A message into the log, not the UI: `MESSAGE eNNN WITH ... INTO DATA(lv_dummy)` (class/number as literals, see "Error handling") then `lo_msglist->add_symsg( ).` `add_symsg` picks up `sy-msgid/sy-msgty/sy-msgno/sy-msgv1..4` of the last `MESSAGE`.
- **[P2]** Direct add (without `MESSAGE INTO`, e.g. in `CATCH`): `lo_msglist->add( is_message = VALUE #( msgty = sy-msgty msgid = sy-msgid msgno = sy-msgno msgv1 = sy-msgv1 ... ) ).`
- **[P2]** Accumulate messages, do not stop on the first: accumulate in a loop, show at the end. Presence of a needed type: `lo_msglist->has_messages_of_msgty( iv_msgty = 'E' )` (on the standard interface; `has_message( ... )` is a project wrapper's method); the list is **empty** — `is_empty( ) = abap_true` (i.e. `is_empty( ) = abap_false` means there are messages — do not confuse the labels).
- **[P2]** Binding to a row/field — via `id_tabname`/`id_fieldname`/`id_context` on `add_symsg`/`add`; check for a bound message — via the standard query methods (`has_messages_of_msgty` / `get_message_list` with the context), or the project wrapper's `has_message( it_cfil = ... )`.
- **[P3]** Show: `cl_log_ppf=>show_log( lo_msglist->get_handle( ) )` (display by handle; `display( iv_popup )` is a project wrapper convenience). Save into the Application Log: `lo_msglist->store( if_in_update_task = abap_false )` (in the update task — `abap_true`).
- **[P2]** `lo_msglist->clear( )` before a new chunk/pass — otherwise messages of the previous iteration stick and duplicate.
- **[P1]** `CATCH cx_reca_symsg` — add to the log, do not swallow silently and do not pass off as success (see "Error handling": an empty `CATCH` is forbidden). <!-- rule: catch-reca-symsg-log -->
- **[info]** Show the accumulated Application Log by handle: `cl_log_ppf=>show_log( lo_msglist->get_handle( ) )`.
- **[P2]** Mass processing (a loop over many rows/objects) — do not write a log entry per iteration: accumulate and add via `add`/`add_symsg` once per chunk or per aggregate — `cl_reca_message_list` and the Application Log (SLG1) cost memory and slow the run.
- **[info]** Low-level BAL (no RE-FX, or when you hold a raw `bal_s_log` header/handle): `BAL_LOG_CREATE` (header `i_s_log` — `object`/`subobject`/`extnumber`/`aldate_del` for the retention date → `e_log_handle`), `BAL_LOG_MSG_ADD` (`i_log_handle` + `i_s_msg` = `msgty`/`msgid`/`msgno`/`msgv1..4` → `e_s_msg_handle`), `BAL_DB_SAVE` (`i_t_log_handle` → `e_new_lognumbers`, `i_in_update_task` to persist inside the update task), `BAL_DSP_LOG_DISPLAY` (`i_t_log_handle`), `BAL_LOG_HDR_READ` (to re-read/refresh the header). This is the fallback when `cl_reca_message_list` is absent.
- **[info]** Application Log (SLG1) entries persist in the DB (`BALDAT`/`BALHDR`/`BALM`) only after `BAL_DB_SAVE` — an unsaved log exists only in memory and is lost when the work process ends. `BAL_DB_SAVE`/`store` with `if_in_update_task = abap_true` defers the write to the update task — the log is stored by the update task even if the dialog work-process later rolls back; `abap_false` writes it synchronously in the process's own LUW (see `errors.md` for LUW/COMMIT rules).
- **[P2]** Retention: set the deletion date (`aldate_del` in the header, or `cl_reca_message_list` store options / `id_extnumber` + deletion period) — an Application Log written without a retention policy accumulates rows and bloats `SLG1` over time; for long-running mass jobs prefer `aldate_del` ≈ job end + N days over "keep forever".
- **[P3]** Read another program's saved log by external number/object — do not `SELECT` from `BALHDR`/`BALM` by hand; read via the BAL API / the message-list wrapper (look up the handle from the header by object/subobject/external number), which returns the handle for `BAL_DSP_LOG_DISPLAY` and respects the client/authorization of the log display.
- **[P3]** Log text from a message: prefer storing the structured message (`msgid`/`msgno`/`msgv1..4`) over a pre-assembled `string` — the Application Log stores both `msgid/no/v1..4` and a resolved text; storing the raw assembled text loses translation/formatting when the message class changes.
