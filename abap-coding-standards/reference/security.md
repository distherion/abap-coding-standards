# Security

> Dynamic SQL and dynamic names, `AUTHORITY-CHECK` and HR infotype authorization, dynamic code/OS commands, XSS on output, RFC and trusted connections.
> Related: `ldb.md` (the authorization filter the LDB applies itself), `hr-pa.md` (the class-based PA check), `hr-pa-write.md` (the write path), `files-io.md` (file paths, encodings), `dynamic-rtti.md` (a dynamic name is an injection).

- **[P0]** Never concatenate external input (UI fields, RFC parameters, files) into a SQL string — SQL injection. A dynamic SQL fragment is safe only when it is a literal in the code or has passed a whitelist check; a value goes in as a host variable (`@`) or an ADBC `SET_PARAM`, never as concatenated text. <!-- rule: no-sql-string-concat -->
  ```abap
  " wrong — the input becomes part of the statement text
  SELECT pernr FROM pa0001 WHERE pernr = '" && lv_pernr && "' INTO TABLE @lt_pa0001.

  " right — a host variable, the statement text stays constant
  SELECT pernr FROM pa0001 WHERE pernr = @lv_pernr INTO TABLE @lt_pa0001.
  ```
- **[P2]** Dynamic SQL — only when static is impossible. Hierarchy: static Open SQL → dynamic Open SQL with `CL_ABAP_DYN_PRG` (`quote`/`quote_str`/`escape_quotes`/`escape_quotes_str`/`check_table_name_str`/`check_column_name` (with optional `strict`; **does not exist:** `check_column_name_str`)/`check_whitelist_str`/`check_whitelist_tab`) → ADBC (`?`-placeholders + `SET_PARAM`, still no concatenation). **does not exist:** `?`/`USING` parametrized statements in ABAP SQL — parameters in Open SQL are `@`-host variables.
- **[P1]** Dynamic names/tokens (`(tabname)`, `(colname)`, `ASSIGN (lv)`, `CALL FUNCTION lv_function` — both `lv_function` and the parenthesized `(lv_function)` are valid dynamic FM-name forms, prefer the unparenthesized one; `(lv_comp)-field`) and dynamic `WHERE`/`HAVING` — the name source is not external (UI/RFC/file), validate against a whitelist; handle `cx_sy_dynamic_osql_syntax`/`cx_abap_invalid_name`/`cx_abap_not_in_whitelist`/`cx_sql_exception` (**does not exist:** `cx_abap_dyn_prg_illegal_value`). <!-- rule: dynamic-names-whitelist -->
- **[P1]** `HR_READ_INFOTYPE_AUTHC_DISABLE` disables the P_ORGIN check for exactly one subsequent `HR_READ_INFOTYPE` call. **does not exist:** a standard `..._AUTHC_ENABLE` or a persistent toggle — each call that needs the bypass must be preceded by its own `DISABLE`. Use only when you have verified authorization yourself (via `HR_CHECK_AUTHORITY_INFTY` — this is a **standard** FM on the target system — or PNP). There is no stable off/on for PA. `RH_AUTHORITY_CHECK_OFF`/`RH_AUTHORITY_CHECK_ON` — only for OM/PD structural authorization (`RH_*` FMs, OOSP/OOSB), unrelated to `P_ORGIN`/PA infotypes. <!-- rule: hr-auth-disable-one-shot -->
- **[P2]** HR infotype authorization: `HR_READ_INFOTYPE` checks **P_ORGIN** automatically; `HR_INFOTYPE_OPERATION`/`HR_MAINTAIN_MASTERDATA` check P_ORGIN depending on the infotype and OOAC configuration. In LDB-PNP the LDB itself runs the HR authorization filter (`P_ORGIN`/`P_ORGXX` via BAdI `HRPAD00AUTH_CHECK`, see `ldb.md`). `P_PERNR` (the "own" personnel number) is a **separate** authorization object (OOAC switch `P_PERNR`), not covered by `P_ORGIN` — but it is not a simple "additional positive permission": depending on the `P_PERNR` assignment it can *add or remove* rights on the user's own PERNR, so a mechanical extra `AUTHORITY-CHECK` would change the effective rights and produce false denials. For manual reads route through the central mechanism (`cl_hrpad00auth_check_std`, see below). The read/write *mechanism* choice (framework vs `HR_READ_INFOTYPE`) — see `hr-pa.md`. Direct Open SQL to HR tables (`pa0001`…) bypasses the auto-check — check authorization manually for both read and write via `HR_CHECK_AUTHORITY_INFTY` or `cl_hrpad00auth_check_std`. Switching the API-level check off (`no_auth_check = abap_true` at `if_hrpa_read_infotype~read_*`, the `AUTHC_DISABLE` FM above) — only where you verified authorization yourself.
- **[info]** Wider PA authorization family beyond `P_ORGIN`/`P_PERNR`: `P_ORGINCON` (`INFTY`/`SUBTY`/`AUTHC`/`PERSA`/…), `P_ORGXX` (PA data without org-unit check), and the per-infotype `P_<INFTY>`-context. Class-based central check — `cl_hrpad00auth_check_std` (`auth_switch_p_orgin`), reusable in explicit enhancements.
- **[P1]** Class-based PA check for your own case (own container, or a call with `no_auth_check`): `cl_hrpad00auth_check_factory=>get_auth_checker( EXPORTING context TYPE hrpad00auth_context mode TYPE hrpad00auth_mode disable_timelogic OPTIONAL EXPORTING auth_checker TYPE REF TO if_ex_hrpad00auth_check )` `RAISING cx_hrpa_violated_postcondition` (the BAdI `HRPAD00AUTH_CHECK` instance), then `cl_hrpa_authorization` (`create public`; constructor takes that BAdI, `RAISING cx_hrpa_violated_assertion`): `check_read( container message_handler → is_authorized )`, `check_insert( )`, `check_modify( old_container container … )`, `check_delete( )` — the same check the framework runs. Use it instead of a hand-written `AUTHORITY-CHECK` over `P_ORGIN` fields: a denial comes back through `is_authorized` **and** the message handler, read both. <!-- rule: hrpa-auth-check-class -->
- **[P1]** `AUTHORITY-CHECK` — for the action and before data access. Only transaction/report/RFC start and `S_TABU_DIS` (in table maintenance tools / the table viewer) are auto-checked; cover internal actions yourself. Grant access only on `sy-subrc = 0`; `4`/`12` — no rights (note that `12` can also mean the authorization object itself does not exist or is incorrectly maintained) — abort with a message, do not continue. <!-- rule: authority-check-action -->
- **[P2]** Do not modify standard SAP tables directly (`INSERT`/`UPDATE`/`DELETE`) — only via BAPI/API/classes. A direct write breaks invariants and does not survive an upgrade. You may modify your own `Z`-tables.
- **[P1]** `CALL 'C-function'` (kernel call) is forbidden — bypasses all checks, a direct call into the C kernel. Do not use. `CALL 'SYSTEM'` is a kernel call too, but its defect is the OS command it runs — that is the P0 rule below. <!-- rule: no-kernel-call -->
- **[P0]** `CALL TRANSACTION ... WITHOUT AUTHORITY-CHECK` — the addition switches off the automatic check of the called transaction, i.e. an authorization bypass. Blocker when the transaction code or the parameters come from external input (UI/RFC/file) and no explicit `AUTHORITY-CHECK` runs in the same program; in the general case (P2, not a blocker) it is legal only after an explicit `AUTHORITY-CHECK`, and never with a transaction code that is not a literal. <!-- rule: no-authority-check-bypass -->

# Output and encoding (XSS)

- **[P2]** Output of external data into HTML/XML/JS/URL/CSS — encode it: `cl_abap_dyn_prg=>escape_xss_xml_html( val )` / `escape_xss_javascript` / `escape_xss_url` / `escape_xss_css`. Built-in `escape( val = ... format = cl_abap_format=>e_xss_ml )` is also available in 7.50 (see `style.md`). WebDynpro/BSP encode themselves — do not duplicate manually.

# Dynamic files, code and OS commands

- **[P1]** A file name/path from external input in `OPEN DATASET`/`DELETE DATASET` — path traversal. Do not concatenate external input into a path: logical names via `FILE_GET_NAME`, or validation `FILE_VALIDATE_NAME( logical_filename = ... )` (requires a logical name, only absolute paths); otherwise manual filtering of `../`/`..\` + a whitelist of extensions/directory. <!-- rule: open-dataset-path-traversal -->
- **[P0]** Dynamic generation/loading of code with external content — `GENERATE SUBROUTINE POOL`, `INSERT REPORT`, `READ REPORT`, `SYNTAX-CHECK` — arbitrary code execution (= `SAP_ALL`). Do not use for external input; instead of `INSERT REPORT` from text — a static report. <!-- rule: no-dynamic-code-gen -->
- **[P0]** Executing OS commands: `CALL 'SYSTEM'`, `OPEN DATASET ... FILTER`, `cl_gui_frontend_services=>execute` — command injection, unsafe even without external input. For external commands — only SXPG with a logical command name. The lower-level `SXPG_STEP_XPG_START` takes a raw OS command path — use only with a fixed command list, never external input. `CALL 'SYSTEM'` is silenced by profile `rdisp/call_system`. <!-- rule: no-os-command-injection -->

# RFC and trusted systems

- **[P2]** `CALL FUNCTION ... DESTINATION` — the RFC authorization is checked by the target system itself; in the destination use a dedicated communication user, not `DDIC`/`SAP*`. A trusted connection (`SMT1`) is controlled by its own ACL, maintained in `SMT1`.
