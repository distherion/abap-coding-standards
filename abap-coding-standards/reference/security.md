# Security

- **[P2]** Dynamic SQL — only when static is impossible. Never concatenate external input (UI fields, RFC parameters, files) into a SQL string. Hierarchy: static Open SQL → dynamic Open SQL with `CL_ABAP_DYN_PRG` (`quote`/`quote_str`/`escape_quotes`/`escape_quotes_str`/`check_table_name_str`/`check_column_name` (with optional `strict`; there is no `check_column_name_str`)/`check_whitelist_str`/`check_whitelist_tab`) → ADBC (`?`-placeholders + `SET_PARAM`, still no concatenation). ABAP SQL itself has no `?`/`USING` parametrization — parameters in Open SQL are `@`-host variables.
- **[P1]** Dynamic names/tokens (`(tabname)`, `(colname)`, `ASSIGN (lv)`, `CALL FUNCTION lv_function` — both `lv_function` and the parenthesized `(lv_function)` are valid dynamic FM-name forms, prefer the unparenthesized one; `(lv_comp)-field`) and dynamic `WHERE`/`HAVING` — the name source is not external (UI/RFC/file), validate against a whitelist; handle `cx_sy_dynamic_osql_syntax`/`cx_abap_invalid_name`/`cx_abap_not_in_whitelist`/`cx_sql_exception` (there is no `cx_abap_dyn_prg_illegal_value`). <!-- rule: dynamic-names-whitelist -->
- **[P1]** `HR_READ_INFOTYPE_AUTHC_DISABLE` disables the P_ORGIN check for exactly one subsequent `HR_READ_INFOTYPE` call. There is **no** standard `..._AUTHC_ENABLE` and no persistent toggle: each call that needs the bypass must be preceded by its own `DISABLE`. Use only when you have verified authorization yourself (via `HR_CHECK_AUTHORITY_INFTY` — this is a **standard** FM on the target system — or PNP). There is no stable off/on for PA. `RH_AUTHORITY_CHECK_OFF`/`RH_AUTHORITY_CHECK_ON` — only for OM/PD structural authorization (`RH_*` FMs, OOSP/OOSB), unrelated to `P_ORGIN`/PA infotypes. <!-- rule: hr-auth-disable-one-shot -->
- **[P2]** HR infotype authorization: `HR_READ_INFOTYPE` checks **P_ORGIN** automatically; `HR_INFOTYPE_OPERATION`/`HR_MAINTAIN_MASTERDATA` check P_ORGIN depending on the infotype and OOAC configuration. In LDB-PNP the LDB itself runs the HR authorization filter (`P_ORGIN`/`P_ORGXX`/`P_NNNNN` via BAdI `HRPAD00AUTH_CHECK`, see `ldb.md`). `P_PERNR` (the "own" personnel number) is a **separate** authorization object (OOAC switch `P_PERNR`), not covered by `P_ORGIN` — but it is not a simple "additional positive permission": depending on the `P_PERNR` assignment and `PSIGN` handling it can *add or remove* rights on the user's own PERNR, so a mechanical extra `AUTHORITY-CHECK` would change the effective rights and produce false denials. For manual reads route through the confirmed central mechanism (`cl_hrpad00auth_check_std`, see below) and verify the check path in the target system. The read/write *mechanism* choice (framework vs `HR_READ_INFOTYPE`) — see `hr.md`.
- **[info]** Wider PA authorization family beyond `P_ORGIN`/`P_PERNR`: `P_ORGINCON` (`INFTY`/`SUBTY`/`AUTHC`/`PERSA`/…), `P_ORGXX` (PA data without org-unit check), and the per-infotype `P_<INFTY>`-context. Class-based central check — `cl_hrpad00auth_check_std` (`auth_switch_p_orgin`), reusable in explicit enhancements.
- **[P2]** Direct Open SQL to HR tables (`pa0001`…) bypasses the auto-check — check authorization manually for both read and write — via `HR_CHECK_AUTHORITY_INFTY` (a standard FM) or `cl_hrpad00auth_check_std`. Bypassing the auto-check at the API level — only where you verified authorization yourself: FM `HR_READ_INFOTYPE_AUTHC_DISABLE` (see above — one read per call); class-based reader — `no_auth_check = abap_true` at `if_hrpa_read_infotype~read_*`.
- **[P1]** `AUTHORITY-CHECK` — for the action and before data access. Only transaction/report/RFC start and `S_TABU_DIS` (in table maintenance tools / the table viewer) are auto-checked; cover internal actions yourself. Grant access only on `sy-subrc = 0`; `4`/`12` — no rights (note that `12` can also mean the authorization object itself does not exist or is incorrectly maintained) — abort with a message, do not continue. <!-- rule: authority-check-action -->
- **[P2]** Do not modify standard SAP tables directly (`INSERT`/`UPDATE`/`DELETE`) — only via BAPI/API/classes. A direct write breaks invariants and does not survive an upgrade. You may modify your own `Z`-tables.
- **[P1]** `CALL 'C-function'` (kernel call) is forbidden — bypasses all checks, a direct call into the C kernel. Do not use. <!-- rule: no-kernel-call -->
- **[P2]** `CALL TRANSACTION ... WITHOUT AUTHORITY-CHECK` — only after an explicit `AUTHORITY-CHECK`; bypassing the auto-check on external input — P0.

# Output and encoding (XSS)

- **[P2]** Output of external data into HTML/XML/JS/URL/CSS — encode it: `cl_abap_dyn_prg=>escape_xss_xml_html( val )` / `escape_xss_javascript` / `escape_xss_url` / `escape_xss_css`. Built-in `escape( val = ... format = cl_abap_format=>e_xss_ml )` is also available in 7.50 (see `style.md`). WebDynpro/BSP encode themselves — do not duplicate manually.

# Dynamic files, code and OS commands

- **[P1]** A file name/path from external input in `OPEN DATASET`/`DELETE DATASET` — path traversal. Do not concatenate external input into a path: logical names via `FILE_GET_NAME`, or validation `FILE_VALIDATE_NAME( logical_filename = ... )` (requires a logical name, only absolute paths); otherwise manual filtering of `../`/`..\` + a whitelist of extensions/directory. <!-- rule: open-dataset-path-traversal -->
- **[P0]** Dynamic generation/loading of code with external content — `GENERATE SUBROUTINE POOL`, `INSERT REPORT`, `READ REPORT`, `SYNTAX-CHECK` — arbitrary code execution (= `SAP_ALL`). Do not use for external input; instead of `INSERT REPORT` from text — a static report. <!-- rule: no-dynamic-code-gen -->
- **[P0]** Executing OS commands: `CALL 'SYSTEM'`, `OPEN DATASET ... FILTER`, `cl_gui_frontend_services=>execute` — command injection, unsafe even without external input. For external commands — only SXPG (`SXPG_CALL_SYSTEM` with a logical command name). The lower-level `SXPG_STEP_XPG_START` is the common direct variant (raw OS command path) — use only with a fixed command list, never external input. `CALL 'SYSTEM'` is silenced by profile `rdisp/call_system`. <!-- rule: no-os-command-injection -->

# RFC and trusted systems

- **[P2]** `CALL FUNCTION ... DESTINATION`: the target system checks `S_RFC` (fields `RFC_NAME`/`ACTVT`/`RFC_TYPE`); for an explicit check before the call — `AUTHORITY_CHECK_RFC` (catch `RFC_NO_AUTHORITY`/`USER_DONT_EXIST`). In destinations — a dedicated communication user, not `DDIC`/`SAP*`; trusted connections (`SMT1`) are additionally controlled by `S_RFCACL`.
