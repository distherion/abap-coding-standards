# Signatures and method calls

> Method definition vs call order, parameter passing (by reference and by value), type compatibility of an actual against a formal, and the same question for `CALL FUNCTION`.
> Related: `classes.md` (class and method design), `data.md` (`IS BOUND`/`IS INSTANCE OF` before a dereference or a downcast), `testing.md` (test doubles and DI).

- **[info]** **Definition** (`METHODS`): sections strictly in order `IMPORTING → EXPORTING → CHANGING → RETURNING → RAISING`; a violation is a syntax error (`FORM` has only `USING`/`CHANGING`, `FUNCTION` has its own set — SE37 sets the order).
- **[info]** **Call** (parenthesized): `EXPORTING → IMPORTING → CHANGING → RECEIVING`. The call order **differs** from the definition order!
- **[P3]** **Mixed calls**: parameters without a section keyword are input parameters (`do( iv_x = lv )` is the short form of `do( EXPORTING iv_x = lv )` — ABAPDocu "Calling Methods, Short Forms"). `CHANGING` in a call can never be omitted. When the call has an `IMPORTING`/`CHANGING`/`RECEIVING` section, the word `EXPORTING` is mandatory for exported parameters. Examples: `do( iv_x = lv )` (only importing — the word omitted); `do( EXPORTING iv_x = lv RECEIVING rv = lv2 )` (there is RECEIVING — EXPORTING explicit); `do( EXPORTING iv_x = lv CHANGING cs_y = lv2 )`; `do( CHANGING cs_x = lv )`.
- **[P3]** **Formatting calls with parameters** (SAP pretty-printer): the first named parameter — on the line with `(`, the rest one per line; names and `=` aligned into a column across all sections. One parameter (or none) — on one line; two or more — each on its own line:
  ```abap
  mo_service->fill_tech_fields( EXPORTING iv_begda     = lv_begda
                                          iv_endda     = lv_endda
                                 CHANGING cs_db        = ls_db ).
  ```
- **[P3]** The same `=`-alignment in `VALUE`/`NEW`/`CORRESPONDING` constructors; an empty constructor — `VALUE p0001( )`; a short `CORRESPONDING ... MAPPING` — on one line.
- **[P3]** A nested call as an argument value (`method( EXPORTING iv_x = other( ... ) CHANGING cs_y = ... )`): the nested call's parameters, starting on the line `iv_x = other(`, continue in the same `name_col`/`eq_col` as the outer call — one aligned block; the `CHANGING` section of the outer call after the nested call's closing `)` — again in the same `name_col`. Deeper nested expressions in a value (`COND #( ... )`, `VALUE ...( ... )`) align to their own bracket, not to the outer column.
- **[P3]** In calls prefer a functional call or `IMPORTING` over `RECEIVING`; self-reference `me->method( )` → `method( )`.
- **[P3]** ≤3 IMPORTING; one `RETURNING` instead of `EXPORTING` where possible; do not mix `RETURNING`+`EXPORTING`.
- **[P3]** The `RETURNING` parameter — uniform across the project (`result` or `rv_*` per the prefix convention); the name does not repeat the type/value. `PREFERRED PARAMETER` — rarely, do not introduce for one call site.
- **[P2]** A method whose behavior changes by a flag or `IS SUPPLIED` (a boolean parameter, except `SET_*`, and extra `OPTIONAL` parameters) does two things — split into separate methods: `update( )` / `update_and_save( )`, not `update( do_save = abap_true )`.
- **[P2]** Many related parameters (fields of an object, context dependencies, fields of an error) — group into a `ty_*` structure and pass one `is_*`/`cs_*`, not a dozen scalars. An `OPTIONAL` scalar in a structure loses `IS SUPPLIED` — distinguish an optional field with a flag (`has_*`).
- **[P1]** A formal parameter is checked for **type compatibility** (the actual's type must be a subset of the formal's), not for convertibility as in an operand position: a `string`/`c` actual into a parameter typed `NUMC`, `DATS`, `TIMS`, `INT` or `DEC` is a syntax error ("has a type that is incompatible with the formal parameter"), while the same value is assigned without a word in an operand position or in `VALUE`/`CORRESPONDING`. The check is **not symmetric**, and char-like is not automatically compatible: a fixed-length `c`/`n`/`d`/`t` actual into a complete `TYPE string` formal is that same syntax error (a CHAR1/CHAR4 DDIC field — `HRPAD_GENDER`, `SUBTY` — a text symbol), while a `string` actual into a fixed-length `c` formal passes and is converted (a `CONV #( )` added on such a call is then only a redundant-conversion warning). Read the type of the formal from its declaration (or from the DDIC field behind it), never from the call site — and check **every** call site: a formal that one actual fits rejects another. Fix: a generic character type in the formal (`clike`/`csequence`) when the callers differ, otherwise a conversion at the call — `CONV #( ... )` (the type is inferred from the parameter) or a local of the target type. Only the system's syntax check performs this check: static analyzers (abaplint, abapOpenChecks, SonarSource) do not compare actual and formal types, so their clean run proves nothing about the call. <!-- rule: formal-param-type-subset -->
- **[P1]** `IS SUPPLIED` — only for a parameter declared `OPTIONAL`: on a mandatory one it is a syntax error and the object does not activate. Look at the declaration in the class that defines the method — a parameter that was not passed arrives **initial**, so where an omitted value and an empty one mean the same thing, `IS INITIAL` is enough and needs no `OPTIONAL`. <!-- rule: is-supplied-optional-only -->
- **[P0]** The same question for `CALL FUNCTION` has the **opposite** answer: the call is always dynamic, and **the syntax check does not look at the parameter types at all** (only the extended program check does, and only for a constant function name). A formal parameter with a concrete type requires the actual's type to match **exactly** — a mismatch is not converted but ends in a runtime error (`CX_SY_DYN_CALL_ILLEGAL_TYPE`): `CALL_FUNCTION_CONFLICT_TYPE` (type), `CALL_FUNCTION_CONFLICT_LENG` (length — `P LENGTH 8` against `P LENGTH 7` is already a dump), `CALL_FUNCTION_CONFLICT_GEN_TYP` (a generic typing not met), `CALL_FUNCTION_WRONG_ALIGNMENT`. Compared are technical type properties only — component names and DDIC semantics are not, so a structure of the same layout passes under a different name. A generic formal (`TYPE any`/`c`/`n`) is checked as a subset, exactly as for methods. **Expressions are the exception**: a literal, calculation/constructor/function/table expression is converted to the input parameter's type and passed by value — so a foreign-typed variable is fixed by an explicitly typed conversion or by a local variable of the interface's type, and `CONV #( )` is **not** allowed here (a dynamic call derives no type from the FM interface) — only `CONV <type>( )`. <!-- rule: fm-param-type-exact -->
- **[P2]** Large structures/tables in `IMPORTING` without `VALUE` (or `REFERENCE`) are passed by reference; with `VALUE` — passed by value with copy-on-write (the data is not physically copied until the callee writes). If the parameter does not change — do not take it by value.
- **[P1]** A dereference of a reference that can stay empty, and every downcast, needs its guard — `IS BOUND` / `IS INSTANCE OF`; the rule and its scenarios live in `data.md` (`ref-unbound-check`).
- **[P1]** An `IMPORTING` parameter (without `VALUE`) — a reference to the caller's data: do not modify it and do not pass it into another procedure's `CHANGING` (silently corrupts others' data, like `hrtnnnn_tab = it_attrib`). You may modify only an object via `REF TO`. Need to modify the input table/structure — copy to a local variable. <!-- rule: importing-no-value-readonly -->
- **[P1]** An `EXPORTING` parameter without `VALUE`: guarantee a write on all branches or `CLEAR` at the start — otherwise the caller gets stale data; `VALUE`/`RETURNING` are empty by definition, do not clear them. Input and output are the same variable → redesign to `RETURNING` (an early `CLEAR` would eat the input). <!-- rule: exporting-no-value-guarantee-write -->
- **[P3]** `CHANGING` — only to update in place some fields of an already-filled existing variable; do not use it to initially fill a previously empty variable (that is `EXPORTING`/`RETURNING`/a functional call). Do not "return" the result via `CHANGING` when the intent is a fresh value.
